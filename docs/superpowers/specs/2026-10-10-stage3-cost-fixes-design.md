### 2.2 프로젝트 Codex 설정의 적용

- **적용 조건:** Codex는 프로젝트의 `.codex/config.toml`을 신뢰한 프로젝트에서만 적용한다.
- **신뢰 등록:** Codex가 그 폴더에서 대화를 시작할 때(`thread/start`) 스스로 등록한다. 토큰은 쓰지 않는다. 등록 전 `config/read`에서는 프로젝트 층이 "비활성"이었고, 시작 뒤에는 "활성"이었다.
- **첫 대화부터 적용:** 래퍼 첫 호출에서 이미 설정이 적용됐다. 명령의 TEMP, TMP, PYTHONPATH가 설정값과 같았다.
- **신뢰 등록이 래퍼 설정을 바꾸지 않는다:**
  - 실험 대화 기록의 `approval_policy`는 `never`였다.
  - `sandbox_policy`는 `workspace-write`, `network_access: false`였다. 래퍼가 지정한 값 그대로다.
  - 신뢰 등록 뒤 `config/read`의 `approval_policy`와 `sandbox_mode`는 둘 다 값이 없었다(사용자 설정에도 없음).

### 2.3 Codex 하위 에이전트는 설정으로 끌 수 없다

- `features.multi_agent = false`: `codex features list`에는 `false`로 나왔다. 하지만 대화에는 `collaboration.spawn_agent` 등 하위 에이전트 도구 6개가 그대로 있었다.
- 여기에 `agents.max_depth = 0`을 더하고 하위 에이전트를 하나 만들게 했더니 **만들기에 성공했다**(답: "hi").
- 두 대화 기록 모두 `multi_agent_version: v2`였다. 지금 Codex(0.160)의 하위 에이전트는 이 설정들로 막히지 않는다.
- 그래서 사용자 지시대로 지시문과 탐지 경고로 대응한다(5절).

### 2.4 임시 폴더 정리

- **설정:** 프로젝트 설정의 `shell_environment_policy.set`으로 Codex 명령에만 TEMP·TMP(저장소 안 git 무시 폴더)와 PYTHONPATH(보정 모듈 폴더)를 줬다.
- **결과:**
  - `TemporaryDirectory()`의 정리와 `mkdtemp()` 뒤 `shutil.rmtree()`가 모두 샌드박스 안에서 성공했다.
  - 남은 폴더는 없었다.
- **보정 모듈 폴더(저장소 밖):** Codex가 쓰려고 하자 `PermissionError`로 거부됐다.
- **브로커:** 브로커와 Codex 자체의 임시 파일은 옮겨지지 않았다. 브로커 환경을 바꾸지 않았기 때문이다.

### 2.5 외부 연결 도구 (새 발견)

- **무엇이 있었나:** Pro 계정의 Codex 대화에는 `mcp__codex_apps__*` 도구가 수백 개 들어 있었다. 예: Gmail 보내기·지우기, Google Drive 파일 지우기·공유, 사이트 배포.
- **왜 위험한가:** 서버 쪽에서 실행되므로 샌드박스가 막지 않는다. 승인 정책이 `never`라 사람 확인 없이 실행될 수 있다.
- **끄는 방법:** 프로젝트 설정에 `features.apps = false`를 넣자 이 도구가 0개가 됐다.

## 3. 래퍼가 관리하는 프로젝트 Codex 설정 (질문 1 A)

### 3.1 파일과 내용

- 위치: `<저장소>/.codex/config.toml`. 래퍼가 쓰고, git이 무시한다. `project-template/.gitignore`에 `.codex/`를 더한다. 무시되지 않는 기존 저장소면 래퍼가 `.git/info/exclude`에 `.codex/`를 더하고 경고를 남긴다(그대로 두면 새 대화 시작 전 "커밋되지 않은 변경" 검사에 걸린다).
- 내용(래퍼가 만든다):

```toml
# llm-workflow 래퍼가 관리한다. 직접 고치지 않는다.
[features]
apps = false

[shell_environment_policy]
set = { TEMP = '<저장소>\.superpowers\sdd\codex-tmp', TMP = '<저장소>\.superpowers\sdd\codex-tmp', PYTHONPATH = '<플러그인 루트>\scripts\sandbox-python' }
```

- `features.multi_agent`는 넣지 않는다. 효과가 없었고(2.3절), 넣었을 때 다른 동작이 바뀌는지 확인하지 않았다.
- 기존 환경 점검(`checkSandboxConfig`)이 이 파일도 읽는다. 위 내용은 그 규칙(전체 접근, 네트워크 허용, 추가 쓰기 경로 금지)에 걸리지 않는다.

### 3.2 호출 전

1. 래퍼가 위 내용을 파일에 쓴다. 이미 있던 내용이 달랐으면 결과의 `warnings`에 "프로젝트 Codex 설정을 다시 썼다"를 남긴다.
2. 쓴 내용의 해시를 기억한다.
3. 공식 플러그인의 클라이언트로 `config/read`(토큰 없음)를 불러 확인한다: 프로젝트 층이 활성인지, `features.apps`가 `false`인지, `shell_environment_policy.set`이 쓴 값과 같은지.
4. 프로젝트 층이 "비활성"이면(그 폴더에서 Codex를 처음 쓰는 경우) 토큰을 쓰지 않는 대화 시작(`thread/start`, 기록 남기지 않음)으로 신뢰 등록을 한 뒤 다시 확인한다.
5. 그래도 맞지 않으면 종료 코드 5로 멈춘다.

래퍼의 `check` 동작(스킬의 준비 단계에서 한 번 돈다)은 여기에 더해 외부 연결 도구를 코드로 확인한다(17절 13번과 같은 방법).
1. 토큰을 쓰지 않는 대화 시작(`thread/start`, 기록 남기지 않음)을 한다.
2. 그 대화의 `mcpServerStatus/list`에 `codex_apps` 서버나 그 도구가 하나라도 있으면 종료 코드 5로 멈춘다.
호출마다 하지 않는 이유는, 외부 도구 목록을 읽는 데 시간이 걸리고 `config/read`의 `features.apps = false` 확인으로 충분하기 때문이다.

### 3.3 호출 뒤 (질문 1의 추가 조건)

- 래퍼가 파일 내용의 해시를 호출 전과 비교한다. 다르면 커밋하지 않고 종료 코드 3으로 끝낸다. 이유는 "보호 파일 변경: `.codex/config.toml`"이다.

- 다음 호출 전에 래퍼가 파일을 다시 쓰므로, 바뀐 내용이 다음 호출로 이어지지 않는다.

**정리 방법 제안 (사용자 Codex 설정 파일은 사용자 승인 없이 고치지 않는다):**

1. 래퍼에 읽기 전용 동작 `codex-run trust-report`를 둔다.

   - 사용자 Codex 설정 파일에서 지울 줄을 그대로 보여 준다.
2. 실제로 지우는 일은 사용자가 승인한 때에만 한다. 사용자가 직접 지우거나, 승인을 받아 마스터가 그 줄만 지운다. 지우기 전에 설정 파일을 백업한다.
3. 연결부 점검은 지금처럼 매번 새 임시 저장소를 만든다. 그래서 신뢰 목록이 점검마다 하나씩 는다. 고정된 점검 저장소 하나를 다시 쓰게 바꾸면 늘지 않지만, 점검 결과가 이전 상태에 영향을 받을 수 있다. 이번에는 바꾸지 않고 `trust-report`로 관리한다.

## 4. 임시 폴더 처리 (질문 2 A, 보완 1)

조건은 셋이다: Codex가 테스트를 통과시킬 수 있다, 결과물 코드를 샌드박스 사정에 맞춰 바꾸지 않는다, 남은 폴더는 래퍼가 호출 뒤 사용자 권한으로 정리하고 기록한다.

### 4.1 보정 모듈

- **위치:** `<플러그인 루트>/scripts/sandbox-python/sitecustomize.py`. 운영 폴더(저장소 밖)이고, Codex 샌드박스가 쓸 수 없다(2.4절).
- **하는 일:** Windows에서 `tempfile.mkdtemp`의 권한 처리만 바꾼다. 원본은 `os.mkdir(path, 0o700)`이고, Python 3.13에서는 이것이 "만든 사용자만" 권한을 붙인다. 보정본은 `os.mkdir(path)`로 만들어 상위 폴더의 권한을 그대로 물려받게 한다. 이름 짓기, 재시도, 감사 이벤트 등 나머지는 원본과 같다.
- **필요한 내부 함수가 없을 때:** `_sanitize_params`, `_get_candidate_names`가 없는 Python 버전이면 보정하지 않는다. 그때는 예전처럼 정리가 실패할 수 있다.
- **적용 범위:** 프로젝트 설정의 `shell_environment_policy`로 Codex가 실행하는 명령에만 PYTHONPATH를 준다.
  - 마스터의 테스트와 사용자의 실행에는 적용되지 않는다.
  - 마스터의 테스트(보정 없음) 결과를 최종 판단 기준으로 삼는다.
- **대가:**
  - Codex 명령 안의 임시 폴더는 Python의 "만든 사용자만" 제한 대신 저장소 폴더의 권한을 따른다.
  - 프로젝트가 자기 PYTHONPATH를 쓰면 Codex 명령에서는 덮어써진다. 지금 템플릿과 시험 프로젝트에는 해당이 없다.

### 4.2 명령 전용 임시 폴더

- TEMP와 TMP는 `<저장소>\.superpowers\sdd\codex-tmp`다. `.superpowers/sdd/.gitignore`가 이 폴더를 무시한다.
- 래퍼는 호출 전에 이 폴더를 만든다.

### 4.3 호출 뒤 정리와 기록

- 래퍼가 `codex-tmp` 아래의 모든 항목을 사용자 권한으로 지운다. 결과 파일에는 `tempCleanup: { removed: [...], failed: [...] }`로 기록한다.
- 지운 항목이 있으면 `warnings`에 "남은 임시 항목 N개 정리"를 남긴다. 지우지 못한 항목은 경로와 함께 경고로 남긴다.
- 래퍼는 호출 전과 뒤의 저장소 최상위 목록을 비교한다. git에 보이지 않는 새 폴더가 생겼으면 경고를 남긴다(3단계 시험에서 Codex가 임시 폴더를 저장소 최상위로 옮긴 경우). 저장소 안의 폴더는 지우지 않는다.

### 4.4 Codex 공통 지시

래퍼가 모든 지시문 앞에 6절의 공통 규칙을 붙인다. 임시 폴더를 저장소 안 다른 곳으로 옮기지 않는다는 규칙과, 지우지 못한 것은 권한을 바꾸거나 다른 명령으로 다시 시도하지 말고 CONCERNS에 적는다는 규칙이 들어 있다.

## 8. 위험 명령 탐지 (12번, 명세 3단계 9.2절 2번 포함)

네트워크 명령 탐지와 같은 방식으로 Codex 명령 문자열에서 아래를 찾아 경고로 남긴다. 실패로 처리하지 않는다.

| 종류 | 패턴 |
|---|---|
| 프로세스 종료 | `taskkill`, `Stop-Process`, `kill`, `pkill`, `wmic ... delete` |
| 권한 변경 | `takeown`, `icacls ... /grant` `/setowner` `/reset` `/inheritance`, `Set-Acl`, `cacls` |
| 삭제 우회 | `[System.IO.Directory]::Delete`, `[System.IO.File]::Delete` |

- **명령 단어 단위로 맞춘다 (검토 반영 1):**
  - 모든 패턴은 앞뒤가 글자, 숫자, 밑줄, 하이픈, 점이 아닐 때만 맞는다.
  - 그래서 `skill`, `SKILL.md`, `killed`, `Kill-Switch` 같은 단어에는 걸리지 않는다. Codex는 호출마다 스킬 파일을 읽으므로, 이것이 없으면 경고가 쏟아진다.
  - `icacls`의 플래그(`/grant` 등)는 같은 명령 안에 `icacls`가 있을 때만 맞춘다.
- **3단계 시험 기록으로 단위 테스트:**
  - 3단계 시험의 Codex 명령 기록을 테스트 자료 파일로 만든다. 메인 7개와 하위 에이전트 17개, 도구 호출 254회이고, 래퍼가 쓰는 것과 같은 추출 방식을 쓴다.
  - 단위 테스트는 탐지 결과가 이미 아는 진짜 경우와 정확히 같은지 확인한다. 진짜 경우는 10-07 15:26의 `[System.IO.Directory]::Delete`, `takeown.exe`, `icacls ... /grant`다.
  - 그 밖의 오탐은 0이어야 한다. 읽기 전용 `icacls <경로>`는 걸리지 않아야 한다.
  - 자료 파일에는 명령 문자열만 넣는다. 비밀 정보가 없는지 만들 때 확인한다.
- 스킬은 경고를 `progress.md`에 `위험 명령 경고: <종류>: <명령>`으로 남기고, 최종 보고의 "사람 확인" 목록에 넣는다.

## 10. 시작 전·호출 전 한도 확인 (9번, 질문 3 A)

### 10.1 동작

- **새 동작 `codex-run limits --cwd <저장소> --phase plan|execute|call [--tasks N]`**
  - 공식 플러그인의 클라이언트로 `account/rateLimits/read`를 부른다. 토큰을 쓰지 않고, 브로커를 띄우지 않는다.
  - 창마다(창 길이 분 단위) 남은 양(100 − 사용률)을 기준과 비교한다.
  - 종료 코드는 셋이다:
    - 0: 모두 기준 이상
    - 4: 하나라도 기준 미만. 출력에 창, 남은 양, 기준, 풀리는 시각을 적는다.
    - 5: 읽지 못함. 설정 파일에 그 요금제가 없을 때도 5다.
- **스킬:**
  - 계획 작성 전에 `--phase plan`, 실행 시작 전에 `--phase execute --tasks <남은 작업 수>`를 돌린다.
  - 4면 시작하지 않고, 풀리는 시각과 함께 사용자에게 알린다.
- **호출 전 확인:**
  - `start`와 `resume`은 Codex를 부르기 전에 `--phase call` 확인을 스스로 한다.
  - 기준 미만이면 Codex를 부르지 않고 종료 코드 4로 끝낸다. 이유는 "한도 부족(호출 전 확인): <창> 남은 X% < 기준 Y%, 풀리는 시각 <시각>"이다.
  - 이때 스킬은 16절의 멈춤 줄을 쓰고, 사용자에게 "한도가 풀린 뒤 새 세션에서 '이어서 진행'"을 안내한다.

### 10.2 기준값 설정 파일

- **위치:** `plugin/settings/workflow-settings.json`. 운영 폴더에 있으며, Codex가 쓸 수 없는 곳이다.
- **내용:** 요금제(`planType`)별, 창 길이별 기준과 보호 경로 목록.
- **값이 없을 때:** 설정 파일에 그 요금제가 없으면 종료 코드 5로 멈춘다. 다른 요금제 값을 대신 쓰지 않는다. 의도된 동작이며, LLM_WorkFlow의 CLAUDE.md 운영 방식에 "Codex 요금제를 바꾸면 기준값을 먼저 추가한다"를 둔다(검토 반영 4).

```json
{
  "protectedPaths": [".claude/", ".githooks/", "CLAUDE.md", ".codex/"],
  "limits": {
    "plus": {
      "300":   { "plan": 50, "executeBase": 0, "executePerTask": 18, "call": 30 },
      "10080": { "plan": 10, "executeBase": 7, "executePerTask": 3,  "call": 5 }
    },
    "prolite": {
      "10080": { "plan": 5, "executeBase": 5, "executePerTask": 2, "call": 5 }
    }
  }
}
```

- 실행 전 기준은 `executeBase + executePerTask × 작업 수`이고, 최대 100이다.
- 기준값의 의미는 "그 창의 남은 양(%)이 이 값 이상이어야 한다"다.

### 10.3 기준값의 근거

**Plus** (3단계 시험의 호출별 사용량, 하위 에이전트 포함):

| 호출 | 5시간 창 증가 | 주간 창 증가 |
|---|---|---|
| 계획 첫 호출 | 77% → 한도 (미완, +23 이상) | 기록 없음 |
| 계획 이어가기, 계획 수정 | +7, +7 | +1, +2 |
| 구현 Task 1~5 | +16, +9, +18, +15, +15 | +3, +2, +3, +2, +3 |
| 최종 수정 | +27 | +4 |

- 계획 전: 첫 호출 30 안팎과 이어가기·수정 각 7을 더해 5시간 50, 주간 10.
- 실행 전: 작업당 최대 18(5시간), 작업당 3과 최종 수정 4에 여유 3을 더해 주간 `7 + 3 × N`.
- 호출 전: 가장 큰 단일 호출 27보다 조금 큰 30(5시간), 주간 5.

**Pro (`prolite`):**

- **측정 해상도의 한계:**
  - 사용률은 1% 단위 정수다. 확인 실험 전체(약 123만 토큰) 뒤에도 0%였으므로, `prolite`의 주간 1%는 123만 토큰보다 크다. 상한만 얻었다.
  - 비교하면 Plus 주간은 Task 3(152만 토큰)에 3%였으므로 1%가 약 50만 토큰이다.
- **3단계 시험 토큰 (하위 에이전트 포함):**
  - 계획 단계 약 563만(첫 호출 219만, 이어가기 136만, 수정 178만, 하위 30만)
  - 작업당 평균 약 152만
  - 최종 수정 약 413만
- **환산과 기준:** 보수적으로 1% = 123만 토큰으로 환산하면 계획 단계 4.6% 이하, 작업당 1.2% 이하, 최종 수정 3.4% 이하다. 그래서 기준은 다음과 같이 둔다.
  - 계획 전 5 (4.6 올림)
  - 실행 전 `5 + 2 × N` (최종 수정 3.4에 여유, 작업당 1.2 올림에 여유)
  - 호출 전 5 (가장 큰 호출 3.4에 여유)
- **재측정 뒤 다시 정한다:** 재측정은 1,000만 토큰 이상을 쓸 것이므로 사용률이 여러 번 오른다. 그때 토큰당 사용률을 다시 계산해 설정 파일 값을 고친다. 하위 에이전트를 막으면 필요한 양은 더 줄 수 있다(2.7절, 표본 하나).

## 11. 실행 중 질문 규칙 (2번, 질문 2 A)

- `codex-execution`의 "멈추는 경우"를 다음 넷으로 좁힌다: 되돌릴 수 없는 작업, 보안, 작업 공간 밖 영향(병합, push, 게시), 계획 붕괴(어느 쪽으로 가도 추측뿐인 경우).
- 래퍼 종료 코드 3·4·5로 인한 멈춤은 그대로 둔다. Codex 없이는 진행할 수 없기 때문이다.
- 그 밖의 일은 마스터가 판정한다. `progress.md`에 `Ruling:`으로 남기고, 사용자가 직접 확인해야 할 것은 `사람 확인: <항목>` 줄로도 남긴다. 최종 보고에 "사람 확인" 체크 목록으로 모은다.
- **권한에 막힌 일:** 우회하지 않는다. 그 일 없이 판정할 수 있으면 판정·기록하고 "사람 확인" 항목으로 넘긴다. 그 일 없이는 진행할 수 없을 때만 멈추고 묻는다.
- `project-template/CLAUDE.md` 안전 규칙의 "권한 문제로 막히면 우회하지 말고 멈춘 뒤 사용자에게 알린다"를 위 규칙으로 바꾼다. 이 저장소(LLM_WorkFlow)의 CLAUDE.md는 바꾸지 않는다.

## 12. 프로젝트 마스터의 메시지 규칙 (3번)

`project-template/CLAUDE.md`의 소통 절에 둔다. 두 스킬의 보고 단계에서 이를 따른다고 적는다.

- **첫 줄:** 단계와 성격을 표시한다. 예: `[명세 3/6]`, `[기획 · 확인 필요]`, `[개발 중 · 큰 문제]`, `[배포 · 확인 필요]`.
- **질문:** 선택지와 추천안 한 줄로 한다. 여러 개면 한 번에 모은다.
- **보고:** 핵심 세 줄로 하고, 자세한 내용은 `docs/reports/` 아래 파일로 남겨 경로를 적는다.
- **배포 때 확인할 항목:** 짧은 체크 목록으로 준다. "사람 확인" 항목, 경고(네트워크, 위험 명령, 하위 에이전트), 판정 목록을 포함한다.

## 13. 계획 검토 관문 기본 해제 (1번)

- `codex-planning` 5단계: 명세 머리말에 `계획 검토: 요청` 줄이 있을 때만 사용자 계획 검토 관문을 연다. 없으면 Opus 검수가 승인한 뒤 바로 `codex-execution`으로 넘어간다.
- `project-template/CLAUDE.md`에 규칙을 둔다: 사용자가 명세 단계에서 계획 검토를 원하면 마스터가 명세 머리말에 그 줄을 넣는다.
- 근거: 3단계 시험에서 사용자는 관문에서 수정을 요청하지 않았다. 관문의 비용은 21시간 대기와 캐시 재작성(약 $0.57)이었다.

## 14. 명세 경계 조건 점검 (5번)

`project-template/CLAUDE.md`에 한 줄을 둔다: "명세를 쓸 때 출력 인코딩, 줄 나누기, 반올림, 표기 예시를 정했는지 확인한다." 4단계에서 도메인 프로필로 옮긴다. 재측정은 같은 명세를 쓰므로 비용 비교에는 영향이 없다.

## 15. 마스터의 기계적인 일을 스크립트로 (7번)

새 스크립트 `plugin/scripts/codex-task.mjs`를 두고, 스킬이 이것을 부르게 한다.

| 동작 | 하는 일 | 대신하는 마스터 일 (3단계 시험 기준) |
|---|---|---|
| `run` | Superpowers `task-brief`로 작업 지시 파일 만들기 → 지시문 틀(implement/fix/final-fix/handoff) 채우기 → 래퍼 호출 → 결과 요약 출력 → 진행 기록 줄 쓰기 | 지시·맥락 파일 작성, 래퍼 실행, 결과 읽기 |
| `review` | Superpowers `review-package`로 검수 자료 만들기 → 검수 틀 채워 지시 파일로 저장 → 경로 출력 | 검수 준비 |
| `ledger` | 정해진 형식의 진행 기록 줄 쓰기(16절) | 진행 기록 |

- **`run`의 입력:** 계획 파일, 작업 번호, 역할, 라운드, 대화 ID(이어가기), 추론 강도, 그리고 마스터가 쓴 맥락 파일(`{{CONTEXT}}`에 들어갈 판정과 인터페이스).
- **`run`의 출력:** 결과 요약 몇 줄(상태, 커밋, 테스트 줄, 우려, 경고, 토큰)과 "다음 할 일" 한 줄(예: "검수로: `codex-task review --task 3`").
- **검수자 호출:** 마스터가 한다. 검수 지시 파일 경로만 넘긴다.
- **기대 효과:** 작업 하나의 마스터 호출이 약 10회에서 3~4회로 준다(`run` 1, `review`와 검수자 호출 1~2, 판정·기록 1).
- **Codex로 옮길 일:** 찾지 못했다(추가 분석 1절). 마스터에게는 검수자 호출, 판정, 사용자 보고만 남긴다.
- **실행 방식:** 래퍼는 지금처럼 백그라운드로 돌리고 알림을 기다린다. 끝나면 요약 한 번만 읽는다.

## 16. 재개 절차 (8번)

### 16.1 진행 기록 줄 형식 (추가분)

| 줄 | 쓰는 때 |
|---|---|
| `Final review: <결과> — findings <파일>` | 최종 검수가 끝난 뒤 |
| `Final fix: codex thread <ID> — <상태>, commit <해시>` | 최종 수정 호출 뒤 |
| `Final re-review: <결과>` | 재검수 뒤 |
| `Usage log: commit <해시>` | 사용량 기록 커밋 뒤 |
| `Broker: closed` | 브로커를 닫은 뒤 |
| `멈춤: <원인> — <재개 조건> — <다음 명령>` | 멈출 때마다. 다음 명령은 전체 인자를 쓴다 |
| `재개: <시각>` | 재개할 때 |

계획 단계(`planning.md`)에도 같은 `멈춤`·`재개` 줄과 `Plan: committed <해시>`, `Plan review: <결과>` 줄을 쓴다.

### 16.2 새 세션에서 "이어서 진행"

`project-template/CLAUDE.md`와 두 스킬에 규칙을 둔다.

1. 진행 기록 폴더에서 `planning.md`, `progress.md`를 찾는다. `progress.md`가 있으면 실행 단계, 없으면 계획 단계다.
2. 해당 스킬로 들어가 마지막 줄부터 이어간다. 끝난 단계는 다시 하지 않는다. 특히 충돌 점검 표가 이미 있으면 다시 쓰지 않고, `Final review:` 줄이 있으면 최종 검수를 다시 하지 않는다.
3. 마지막 줄이 `멈춤:`이면 먼저 재개 조건을 확인한다. 한도 멈춤이면 `codex-run limits`를 돌린다.
4. 계획 단계에서 커밋되지 않은 계획 파일이 남은 채 끊긴 경우는 같은 대화를 이어간다(3단계의 Task 6 판정을 규칙으로 올림).

### 16.3 멈출 때의 안내

멈출 때 마스터는 사용자에게 다음을 알린다: 멈춘 이유, 재개 조건(한도면 풀리는 시각), "조건이 풀리면 새 세션에서 '이어서 진행'이라고 입력". 오래 멈춘 뒤 같은 세션을 이어가면 대화 전체를 다시 캐시에 써야 하기 때문이다(3단계 시험 재작성 약 $3.7).

## 18. 재측정 (배포 뒤, 사용자 확인 후)

- 같은 명세로 새 시험 프로젝트를 만든다. 폴더를 만들 때 사용자 승인을 받는다.
- 시작 전에 사용자 확인을 받는다. 재측정 중에는 사용자가 다른 작업에 Codex를 쓰지 않는다.
- 마스터는 Opus 그대로다.
- **보고서의 "바뀐 조건" 목록:**
  - 이 설계의 범위 전부
  - 요금제 변경 (Plus → Pro `prolite`, 한도 창이 5시간+주간에서 주간 하나로)
  - Codex CLI·모델 버전이 3단계와 다르면 그 차이
- **측정:**
  - Claude 토큰과 API 단가 환산(3단계와 같은 방법)
  - Codex 토큰(하위 에이전트 포함)
  - 대기(사용자 응답 대기와 Codex 한도 대기로 나눔)
- **한도 대기 비용의 분리:**
  - Codex 한도 대기 뒤 캐시 재작성 비용을 따로 떼어 낸다.
  - 3단계와 재측정 모두 "한도 대기 비용을 뺀 비용"과 "포함한 비용"을 함께 비교한다.
  - 한도 대기가 줄어든 효과(요금제 변경)가 수정의 효과와 섞이지 않게 하기 위해서다.
- 명세를 그대로 쓰므로 최종 검수의 네 주제 지적은 다시 나올 수 있다. 이번 재측정의 목적은 비용 비교다.

## 19. 위험과 남은 일

- **하위 에이전트:** 설정으로 막지 못한다. 지시와 탐지만 있다. Codex가 지시를 따르지 않으면 토큰은 늘고 경고만 남는다.
- **보정 모듈:** Python 내부 함수(`_sanitize_params`, `_get_candidate_names`)에 기댄다. Python이 바뀌면 보정하지 않고 예전처럼 정리가 실패할 수 있다. 연결부 점검 11번이 이를 잡는다.
- **PYTHONPATH:** 프로젝트가 자기 PYTHONPATH를 쓰면 Codex 명령에서 덮어써진다.
- **공식 플러그인 내부 의존 증가:** `CodexAppServerClient`, `config/read`, `account/rateLimits/read`, `thread/start`에 기댄다. 버전 고정과 연결부 점검으로 막는다.
- **신뢰 목록:** 점검과 실험 때마다 는다. `trust-report`로 보고, 정리는 사용자 승인 후에 한다.
- **외부 연결 도구:** `features.apps = false`는 프로젝트 설정에만 넣는다. 사용자의 다른 Codex 작업에는 영향이 없다.
- **4단계 할 일:** 명세 시작 때 예상 질문 수·시간 안내(4번), 보호 경로의 프로젝트별 확장, 경계 조건 목록의 도메인 프로필 이동.
- **자체 개발 결정 때 다룰 후보 (2026-10-11 기록, 지금은 만들지 않음):**
  - Claude 작업자의 저장소 밖 쓰기를 코드로 막는다. 방법 예: Bash 명령의 쓰기 대상 경로(`>` 리다이렉트, `mv`, `cp`, `mkdir` 등)를 검사해 작업 폴더 밖이면 막는 PreToolUse 훅. 근거: 지시문으로 금지했는데도 저장소 밖 쓰기가 두 번 있었고, 두 번 모두 Claude 작업자였다(3단계 작업자 교체 명세의 사례 2 `D:\tmp_unused`, 사례 3 `sub.tmp.mjs`).
  - 작업 폴더가 플러그인 폴더를 포함하면 래퍼가 멈추는 장치(최종 검수 지적 11, 보류). LLM_WorkFlow를 프로젝트로 쓰면 Codex가 기준값 설정 파일과 보정 모듈을 고칠 수 있기 때문이다.
