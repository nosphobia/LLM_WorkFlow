# 3단계 설계: 작업자를 Codex로 교체

- 날짜: 2026-10-05
- 상태: 사용자 검토 대기
- 브랜치: `stage3-design`
- 근거 자료: `docs/에이전트 워크플로우 구축 계획 — 빠른 참고.md`, `docs/2026-10-05 Codex 연결부 탐색 보고서.md`

## 1. 목적과 범위

기획(계획 작성)과 개발(작업 구현)의 작업자를 Claude 서브에이전트에서 Codex로 바꾸고, Claude는 검수만 하게 한다. Superpowers 원본 파일은 고치지 않고, 바꿀 두 단계만 우리 스킬로 대신한다.

### 3단계에서 바꾸는 것

| 단계 | 2단계 (Superpowers 기본형) | 3단계 |
|---|---|---|
| 명세 | Claude 마스터와 사용자 | 같음 |
| 기획 | Claude 마스터가 계획 작성, 자체 점검 | Codex가 작성, Claude가 명세와 대조해 검수, 큰 작업은 사용자 검토 |
| 개발 | Claude 서브에이전트가 구현, Claude가 검수 | Codex가 구현과 모든 수정, Claude가 검수 |
| QA, 위키, 병합 | Claude 마스터 | 같음 (4단계에서 바꾼다) |

### 범위 밖

- QA와 위키 자동화, 기록 보관 체계, 마스터 층, 병합 관문 스크립트, 도메인 프로필 (4단계)
- 한도 도달 후 자동 재개, 병렬 처리 (5단계)
- `project-template` 반영: 비교 시험이 성공한 뒤에 한다
- Superpowers를 6.4.1보다 새 버전으로 올리는 일: 비교 시험 뒤 양쪽을 함께 올린다

### 3단계에만 적용하는 운영 규칙 변경

설계 문서의 수정 루프는 "4~5라운드 후에도 안 되면 Claude Opus 투입"이다. 3단계에서는 이것을 쓰지 않는다. 작성과 수정은 끝까지 Codex만 하고, 5라운드 뒤에도 남은 지적은 마스터가 판정하고 기록한 뒤 보고한다.

## 2. 구성 요소

이 저장소의 `plugin/`에 Claude Code 플러그인 `llm-workflow`를 만든다. `plugin/`을 이 저장소 안의 로컬 마켓플레이스로 등록해 사용자 범위로 설치한다.

```
plugin/
  .claude-plugin/plugin.json
  scripts/
    codex-run.mjs        # 래퍼: Codex 플러그인을 부르는 유일한 곳
    codex-check.mjs      # 연결부 점검 스크립트
    lib/                 # 래퍼의 판단 로직 (보고 해석, 종료 코드, 커밋 대상 검증, 설정·버전 점검)
    test/                # node:test 테스트
  skills/
    codex-planning/      # superpowers:writing-plans 대신
    codex-execution/     # superpowers:subagent-driven-development 대신
```

### 2.1 우리 스킬을 쓰게 하는 방법

각 프로젝트의 CLAUDE.md에 "계획 작성은 `llm-workflow:codex-planning`, 실행은 `llm-workflow:codex-execution`을 쓴다. `superpowers:writing-plans`와 `superpowers:subagent-driven-development`는 쓰지 않는다"는 규칙을 넣는다. CLAUDE.md의 사용자 규칙은 스킬 지시보다 우선하므로, Superpowers의 설계 스킬이 끝에서 `writing-plans`를 부르라고 해도 우리 스킬로 넘어간다.

### 2.2 Superpowers 원본의 재사용

원본은 고치지 않고 고정된 6.4.1 설치 경로에서 그대로 참조한다.

| 원본 (6.4.1) | 쓰는 곳 |
|---|---|
| `skills/subagent-driven-development/scripts/sdd-workspace`, `task-brief`, `review-package` | 진행 기록 폴더, 작업 지시 파일, 검수 자료 묶음 |
| `skills/subagent-driven-development/implementer-prompt.md` | Codex 구현 지시문의 바탕 |
| `skills/subagent-driven-development/task-reviewer-prompt.md`, `re-review-prompt.md` | 작업별 검수, 수정분 재검수 |
| `skills/writing-plans/plan-document-reviewer-prompt.md` | 계획 검수 |
| `skills/requesting-code-review/code-reviewer.md` | 브랜치 전체 최종 검수 |
| `skills/finishing-a-development-branch` | 병합 방식 선택 (바꾸지 않는 스킬) |

### 2.3 버전 고정

| 대상 | 고정 버전 | 방법 |
|---|---|---|
| Superpowers (Claude Code) | 6.4.1 (`5bf4e78`) | 현재 설치 유지, 공식 마켓플레이스 자동 갱신을 끈다 |
| Superpowers (Codex) | 6.4.1 (`5bf4e78`) | 원본 저장소를 같은 커밋으로 Codex 마켓플레이스에 추가해 설치하고, 원격 목록판(6.4.2)은 제거한다 |
| Codex 플러그인 (Claude Code) | 1.0.4 (`807e03a`) | 현재 설치 유지, 래퍼가 버전을 확인한다 |

정확한 명령(자동 갱신을 끄는 방법, Codex 마켓플레이스 이름)은 구현 계획에서 확인한다. 설치 설정을 바꾸는 작업이므로 계획 검토 때 사용자 승인을 받는다.

## 3. 래퍼 `codex-run.mjs`

### 3.1 역할

- Codex 플러그인을 직접 부르는 유일한 곳이다. 플러그인이 바뀌면 래퍼만 고친다.
- 플러그인 내부 라이브러리(`scripts/lib/codex.mjs`의 `runAppServerTurn`, `interruptAppServerTurn`)를 불러 쓴다. 명령줄 `task`는 대화 ID를 지정할 수 없어서 쓰지 않는다.
- 마스터는 Claude Code의 백그라운드 실행으로 래퍼를 돌리고, 끝나면 오는 알림을 받는다. 짧은 작업도 120초를 넘기 때문이다.

### 3.2 입력

- 동작: `start`(새 대화), `resume`(대화 ID 지정), `check`(3.3절 1번 환경 점검만 하고 끝냄)
- 저장소 경로, 지시 파일 경로, 진행 기록 폴더 경로
- 역할(`plan`, `plan-fix`, `implement`, `fix`, `final-fix`), 작업 번호, 라운드
- 선택: 추론 강도(기본은 Codex 설정값), 제한 시간(기본 30분)

### 3.3 처리 순서

1. **환경 점검.** 하나라도 어긋나면 종료 코드 5로 멈춘다.
   - Claude Code 쪽 Codex 플러그인이 1.0.4이고 라이브러리 파일이 있다.
   - Claude Code 쪽 Superpowers가 6.4.1이다.
   - Codex 쪽 Superpowers가 6.4.1이다 (`codex plugin list`).
   - Codex 설정(`~/.codex/config.toml`과 저장소의 `.codex/config.toml`)에 샌드박스 경계를 넓히는 설정이 없다 (3.6절).
2. **Codex 호출.** 쓰기 샌드박스(`workspace-write`), 승인 요청 없음(`never`)으로 실행한다. `resume`이면 지정한 대화 ID로 이어가고, 돌아온 ID가 다르면 실패(3)로 처리한다.
3. **제한 시간.** 넘기면 Codex 실행을 중단시키고 실패(3)로 끝낸다. Windows에서는 차례를 중단해도 Codex가 띄운 명령이 계속 돌 수 있다(8절). 그래서 중단 직후 저장소 상태를 기록하고, 2분 기다린 뒤 다시 비교해 그 사이 바뀐 파일을 결과의 `lateChanges`에 남긴다. 확인이 실패해도 "제한 시간" 이유는 유지한다.
4. **호출 실패 판별.** 예외, Codex 오류 필드, 차례가 정상 완료가 아닌 경우는 실패(3)다. 단, 차례가 정상으로 끝났으면 Codex가 재시도한 일시 오류(재연결 등)는 실패로 보지 않고 결과의 `transientError`에 남긴다. 그중 오류 메시지나 Codex 세션 기록의 한도 정보(`rate_limit_reached_type`)가 한도 도달을 가리키면 한도(4)다.
5. **보고 해석.** Codex 최종 메시지에서 아래 보고 형식(3.4절)을 읽는다.
6. **형식 위반 정정.** `STATUS` 줄이 없거나 해석할 수 없으면 같은 대화에 정정을 한 번 요청한다. 그래도 안 되면 실패(3)다.
7. **커밋.** `STATUS`가 `DONE` 또는 `DONE_WITH_CONCERNS`이면:
   - `CHANGED_FILES`와 실제 변경(git의 변경·새 파일, git이 무시하는 파일 제외)을 비교한다.
   - 다르면 같은 대화에 정정을 한 번 요청한다. 그래도 다르면 커밋하지 않고 실패(3)다.
   - 같으면 그 파일만 커밋한다. 메시지는 `COMMIT_MESSAGE`이고, 마지막 줄에 세션 기록의 실제 모델명으로 `Co-Authored-By: Codex <모델명> <noreply@openai.com>`을 붙인다.
   - `CHANGED_FILES`가 비어 있으면 커밋하지 않는다.
8. **사용량 기록.** 세션 기록 `~/.codex/sessions/**/rollout-*-<대화 ID>.jsonl`에서 이번 호출 전후의 누적 토큰과 한도 사용률을 읽어 진행 기록 폴더의 `codex-calls.jsonl`에 한 줄 추가한다.
9. **결과 출력.** 전체 결과를 결과 파일(JSON)에 쓰고, 표준 출력에는 한 줄 요약만 쓴다.
10. **네트워크 명령 탐지.** 세션 기록에서 이번 호출의 차례들이 실행한 명령을 읽어, 네트워크를 쓰는 명령(패키지 설치, 다운로드, 원격 git 등)을 결과의 `networkCommands`와 `warnings`에 남긴다. 종료 코드는 바꾸지 않는다. 막지는 못하고 탐지만 한다(3.6절).

### 3.4 Codex 보고 형식

Codex의 최종 메시지는 아래 줄로 끝나야 한다. 지시 파일마다 이 형식을 넣는다.

```
STATUS: <DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED>
CHANGED_FILES: <저장소 기준 상대 경로를 쉼표로 구분, 없으면 none>
COMMIT_MESSAGE: <한 줄 커밋 메시지, 커밋할 것이 없으면 none>
TESTS: <실행한 명령과 결과 줄, 없으면 none>
CONCERNS: <내용, 없으면 none>
```

Codex는 커밋하지 않는다. 샌드박스가 `.git` 쓰기를 막기 때문이고, 커밋은 래퍼가 한다.

### 3.5 종료 코드

| 코드 | 의미 | 마스터의 처리 |
|---|---|---|
| 0 | 완료 (`DONE`, `DONE_WITH_CONCERNS`), 커밋됨 | 검수로 넘어간다 |
| 2 | Codex가 `NEEDS_CONTEXT` 또는 `BLOCKED`를 보고 | 5.3절 |
| 3 | 실패: 호출 실패, 예외, 제한 시간 초과, 대화 ID 불일치, 형식 위반 정정 실패, 보고와 실제 변경 불일치 | 멈추고 보고한다 |
| 4 | 한도 도달 | 멈추고 보고한다 |
| 5 | 환경 점검 실패: 버전 불일치, 샌드박스 경계 설정 위반 | 멈추고 보고한다 |

3, 4, 5에서 Claude는 대신 구현하지 않는다.

### 3.6 Codex 샌드박스 경계

Claude Code의 차단 규칙(`.claude/settings.json`)은 Codex에 적용되지 않는다. Codex의 경계는 Codex 샌드박스가 정한다.

| 경계 | 기대값 | 래퍼 시작 시 확인 | 점검 스크립트의 실제 확인 |
|---|---|---|---|
| 쓰기 범위 | 저장소 폴더만 | 추가 쓰기 경로(`writable_roots`) 설정 없음, 전체 접근 모드(`danger-full-access`) 설정 없음 | 저장소 밖 파일 쓰기가 거부됨 |
| 네트워크 | 꺼짐 (Codex 설정). **Windows `unelevated` 샌드박스는 실제로 막지 못한다 (알려진 한계)** | 네트워크 허용(`network_access = true`) 설정 없음 | 외부 접속 결과를 기록만 한다. 래퍼가 네트워크 명령을 탐지해 경고로 남긴다 |
| `.git` | 읽기 전용 | (설정으로 바꿀 수 없음) | `.git` 쓰기가 거부됨 |
| 승인 요청 | 없음 (`never`) | 래퍼가 항상 `never`로 호출 | 해당 없음 |

push는 네트워크 차단과 저장소의 pre-push 훅이 함께 막는다.

### 3.7 테스트

판단 로직(보고 해석, 종료 코드 결정, 커밋 대상 비교, 설정과 버전 점검, 세션 기록 읽기)은 `lib/`에 순수 함수로 두고 `node:test`로 시험한다. 실제 Codex 연결은 점검 스크립트로 시험한다.

## 4. 계획 작성 스킬 `codex-planning`

1. **준비.** 명세가 승인된 뒤 시작한다. 래퍼의 환경 점검을 돌린다. 사용자에게 Claude 주간 사용률(측정점 1)을 받는다. Codex 쪽은 첫 호출의 세션 기록에서 자동으로 읽는다.
2. **Codex 계획 작성.** 새 대화로 부른다. 지시 파일에는 다음을 넣는다.
   - 명세 경로, 계획 저장 경로(`docs/superpowers/plans/YYYY-MM-DD-<주제>.md`)
   - Codex 쪽 Superpowers의 계획 작성 규칙(6.4.1)대로 쓸 것, 설계 질문이나 브레인스토밍을 하지 말 것
   - 계획 작성 규칙의 실행 방식 선택 단계는 건너뛸 것
   - 계획 머리말의 실행 스킬 이름은 `superpowers:subagent-driven-development` 대신 `llm-workflow:codex-execution`으로 적을 것
   - 3.4절 보고 형식
   래퍼가 계획 파일을 커밋한다.
3. **Claude 계획 검수.** Superpowers의 계획 검수 프롬프트에 세 가지 점검을 더한다.
   - 명세의 요구사항마다 대응하는 작업이 있는가
   - 명세의 제외 범위를 침범하지 않았는가
   - 작업 수와 크기가 적절한가
   검수 모델은 계획의 크기와 위험도로 고른다. 큰 계획이나 코드 전체가 들어간 계획은 Opus, 작고 위험이 낮은 계획은 Sonnet이다. 이번 비교 시험은 Opus로 한다.
4. **수정 루프.** 5.4절과 같은 규칙이다. 수정분 재검수는 Sonnet으로 한다. Claude는 계획을 직접 고치지 않는다.
5. **사용자 계획 검토 (큰 작업만).** 마스터가 계획 요약, 검수 결과, 판정 목록을 보여 주고 승인을 받는다. 이때 Claude 주간 사용률(측정점 2)을 받아 계획 검수 비용을 따로 기록한다. 승인되면 바로 `codex-execution`으로 넘어간다. 실행 방식과 worktree는 묻지 않는다. 작은 작업은 이 관문 없이 바로 실행한다.

작업 규모는 명세 단계에서 정한다. 설계가 큰 작업 경로(Architectural)였으면 큰 작업이다.

## 5. 실행 스킬 `codex-execution`

### 5.1 준비

- 명세 단계에서 만든 작업 브랜치에서 진행한다. worktree는 만들지 않는다. main 브랜치이면 멈추고 보고한다.
- 진행 기록 폴더(`.superpowers/sdd/<계획>/`)와 진행 기록 파일(`progress.md`)은 Superpowers 스크립트와 형식을 그대로 쓴다. 이 폴더에 Codex 지시 파일, 래퍼 결과 파일, `codex-calls.jsonl`을 더한다.
- 실행 전에 마스터가 계획 안의 충돌을 점검한다 (Superpowers와 같은 절차, 결과는 진행 기록에 표로 남긴다).

### 5.2 작업마다

1. Superpowers 스크립트로 작업 지시 파일을 뽑는다.
2. Codex 지시 파일을 쓴다. 작업 지시 파일 경로, 전체 제약, Superpowers 구현자 규칙(테스트 먼저 쓰기, 자체 점검, 보고 파일 작성), 3.4절 보고 형식, "커밋하지 말 것"을 넣는다. PowerShell 파이프 주의는 넣지 않는다 (비교 시험의 관찰 항목).
3. 래퍼로 새 대화를 시작한다. 진행 기록에 대화 ID를 남긴다.
4. 종료 코드에 따라 처리한다 (3.5절, 5.3절).
5. Superpowers 스크립트로 검수 자료 묶음을 만들어 Claude 작업 검수자(기본 Sonnet)에게 넘긴다. 검수 프롬프트에 규칙 하나를 더한다: 구현자가 보고한 우려마다 판정(타당, 기각, 보류)과 근거를 적는다.
6. 지적이 있으면 수정 루프(5.4절)를 돈다.
7. 진행 기록에 완료 줄을 남긴다. Codex 작업은 동시에 두 개를 돌리지 않는다.

### 5.3 Codex가 보고한 상태의 처리

- `DONE_WITH_CONCERNS`: 마스터가 우려를 먼저 읽는다. 정확성이나 범위에 관한 우려면 같은 대화에서 Codex가 먼저 해결하게 한다. 관찰성 우려면 검수자에게 넘긴다.
- `NEEDS_CONTEXT`: 맥락을 보태 같은 대화로 이어간다.
- `BLOCKED`: 맥락 문제면 맥락을 보태 이어간다. 추론이 부족하면 새 대화에서 추론 강도를 올린다. 작업이 너무 크면 쪼갠다. 계획 결함이면 판정하고 기록한 뒤 다시 맡긴다.

어느 경우에도 Claude가 대신 구현하지 않는다.

### 5.4 수정 루프 (계획과 구현에 공통)

- 한 라운드는 Codex 수정 한 번과 수정분 재검수 한 번이다. 최대 5라운드다.
- 1~3라운드: 같은 Codex 대화를 ID로 이어가며 지적 목록을 넘긴다.
- 4~5라운드: 새 대화에서 추론 강도를 `xhigh`로 올린다. 인계 파일에 현재 계획(또는 코드 위치와 변경 내용), 지금까지의 검수 지적, 시도한 수정 요약을 담는다.
- 수정분 재검수는 크기에 따라 Haiku 또는 Sonnet이다 (계획은 Sonnet).
- 5라운드 뒤에도 남은 지적은 마스터가 판정해 진행 기록에 `Ruling:`으로 남기고, 멈추지 않고 진행한다. 판정 목록은 마지막 보고에 모두 담는다. 결함 때문에 어느 쪽으로 가도 추측뿐이면 멈추고 보고한다.
- 진행 기록에 라운드마다 결과를 남긴다.

### 5.5 마무리

1. **최종 검수.** Claude Opus가 브랜치 전체를 검수한다. 진행 기록의 보류된 사소한 지적 목록도 넘긴다.
2. **최종 수정.** 지적이 있으면 Codex를 한 번만 불러 전체 목록을 고치게 하고, 수정분 재검수를 한 번만 한다. 남은 지적은 판정해서 기록한다.
3. **보고.** 판정 목록 전체, `codex-calls.jsonl` 합계(Codex 토큰, 주간 한도 변화)를 보고하고, Claude 주간 사용률(측정점 3)을 받는다. 기능이 끝나면 `workflow/usage-log.md`에 합계 한 줄을 쓴다.
4. **진행 기록 폴더는 지우지 않는다.** Superpowers 원래 방식(완료 후 삭제)과 다르다.
5. 이후 QA, 위키, 병합은 2단계와 같다. 병합 방식 선택은 `superpowers:finishing-a-development-branch`를 쓴다.

## 6. 연결부 점검 스크립트 `codex-check.mjs`

Codex CLI, Codex 플러그인, Superpowers 버전을 올릴 때마다 다시 돌린다.

- OS 임시 폴더에 작은 Python 저장소를 만들고 래퍼를 통해 아래를 확인한다. 만든 폴더는 지우지 않고 경로를 출력한다.
- 확인 항목:
  1. 환경 점검 통과 (버전, 샌드박스 설정)
  2. Codex가 테스트 먼저 쓰기로 수정하고, 래퍼가 보고된 파일만 커밋하며, 서명 줄에 실제 모델명이 들어감
  3. 한글이 결과에 깨지지 않고 들어옴
  4. 대화 ID로 정확히 이어감
  5. 없는 모델로 부르면 래퍼가 종료 코드 3을 냄
  6. 샌드박스 경계: 저장소 밖 쓰기와 `.git` 쓰기가 거부됨. 네트워크 결과는 기록만 한다 (알려진 한계)
  7. 네트워크를 쓰는 명령을 래퍼가 탐지해 경고로 남김
  8. `codex-calls.jsonl`에 토큰과 한도 사용률이 기록됨
  9. 제한 시간을 넘긴 호출을 래퍼가 중단시키고(종료 코드 3), 중단 뒤 늦게 바뀐 파일을 `lateChanges`로 탐지함 (중단된 명령이 계속 도는 것은 알려진 한계)
- 결과는 항목별 통과·실패 표와 사용한 버전으로 출력한다.

## 7. 비교 시험

### 7.1 시험 전 (이 저장소)

1. 구현 계획대로 `plugin/`을 만들고 설치하고, 버전을 고정한다.
2. 점검 스크립트가 모두 통과해야 다음으로 넘어간다.
3. 설계 문서(`빠른 참고`)에 1절의 3단계 운영 규칙 변경을 기록한다.

### 7.2 시험 (`LLM_Project/usage-log-summary-codex`)

1. `project-template`을 복사하고 CLAUDE.md에 프로젝트 정보와 2.1절 규칙을 넣는다. `git init -b main`, `core.hooksPath` 설정, 최초 커밋을 한다.
2. 2단계 명세 `usage-log-summary/docs/superpowers/specs/2026-10-04-usage-log-summary-design.md`를 내용 그대로 복사해 작업 브랜치에 커밋한다. 이 명세는 2단계에서 승인된 것으로 보고 명세 단계는 건너뛴다.
3. 그 폴더에서 새 Claude 세션을 시작한다. 작업 규모는 큰 작업이다.
4. 진행: 측정점 1 → `codex-planning` → 사용자 계획 검토(측정점 2) → `codex-execution` → 최종 검수와 수정 → 보고(측정점 3) → 병합.
5. QA와 위키는 하지 않는다. 결과물은 병합한 뒤 보관만 한다.

### 7.3 시험 후 (이 저장소)

이 저장소의 세션에서 두 프로젝트의 결과물과 세션 기록을 읽어 `docs/`에 비교 보고서를 쓴다.

| 비교 항목 | 2단계 기준값 |
|---|---|
| 계획의 작업 수 | 5 |
| 테스트 수 | 61 (최종 수정 전) / 64 (최종) |
| 작업별 검수 지적 수, 수정 루프 횟수 | 사소한 지적 11건 보류, 작업별 수정 루프 0회 |
| 최종 검수 결과 | 중요 1, 사소 5 → 4건 수정 |
| 사용량 | Claude: 같은 구간(계획 작성 시작 ~ 구현 끝)의 토큰을 세션 기록에서 뽑는다. 3단계는 계획 검수 비용을 따로 표시한다 (2단계에는 독립 계획 검수가 없었다). Codex: 토큰과 주간 한도 변화 |

관찰 항목: Codex가 PowerShell 파이프 한글 문제를 겪었는지와 처리 방식, Codex가 보고한 우려와 그 판정, 래퍼의 형식 위반 정정 횟수.

### 7.4 성공 기준

1. 계획과 모든 작업이, 수정까지 포함해 "Codex 작성 → Claude 검수"로 끝까지 처리된다.
2. Claude는 코드와 계획을 고치지 않는다. 시험 브랜치에서 코드와 계획 파일을 바꾼 커밋은 모두 Codex 서명 줄을 가진다 (명세 사본 커밋은 예외).
3. 사용자 계획 검토 승인부터 최종 보고까지 사용자에게 질문하지 않는다 (Claude 사용률을 받는 것은 제외).
4. Codex 호출 실패나 한도 초과가 생기면 Claude가 대신 구현하지 않고 멈춰서 보고한다. 이 경로는 시험 전 점검(6절 5번)에서도 확인한다.
5. 시범 세션의 기록(메인과 서브에이전트)에 `superpowers:writing-plans`와 `superpowers:subagent-driven-development` 호출이 없다.
6. 시험 전에 점검 스크립트를 모두 통과하고, 양쪽 Superpowers가 6.4.1로 고정되어 있다.
7. 결과 프로그램의 테스트가 모두 통과하고, 2단계 명세의 성공 기준(실제 기록 파일 처리, 종료 코드 규칙)을 만족한다.
8. 비교 보고서의 모든 항목이 채워진다.

Claude 사용량 감소는 성공 기준에 넣지 않고 비교만 한다. 3단계에는 독립 계획 검수가 더해져 조건이 다르기 때문이다.

## 8. 위험과 미확인 사항

- **한도 도달 메시지:** 실제로 재현하지 못했다. 세션 기록의 한도 정보로 판별하되, 처음 걸렸을 때 래퍼의 판별이 맞았는지 진행 기록으로 확인한다.
- **플러그인 내부 라이브러리 의존:** 공개 명령이 아니라 바뀔 수 있다. 래퍼 한 곳에 가두고, 버전 고정과 점검 스크립트로 막는다.
- **6.4.1 고정 후 Codex 동작:** 탐색은 6.4.2에서 했다. 점검 스크립트로 확인한다.
- **Codex 기본 비용:** 작은 작업 하나에도 약 34만 토큰(대부분 캐시 입력)을 썼다. 비교 시험에서 작업당 비용을 본다.
- **중단 기능:** 제한 시간 초과 때 쓰는 중단 기능은 탐색에서 시험하지 않았다. 래퍼 테스트와 점검 스크립트에서 확인한다.
- **Codex 샌드박스의 네트워크 (알려진 한계, 2026-10-06 확인):** Windows `unelevated` 샌드박스는 설정이 "네트워크 꺼짐"이어도 외부 접속을 막지 못한다(OpenAI 문서: 네트워크 격리가 약함). 방화벽으로 막는 `elevated` 방식은 관리자 승인이 필요하다. 3단계는 한계로 받아들이고 래퍼의 네트워크 명령 탐지, main push 차단 훅, 프로젝트 폴더에 비밀 정보를 두지 않는 규칙으로 대응한다. 5단계(무인 야간 운영) 전에 `elevated`를 다시 검토한다. **이 PC는 예전에 `elevated` 샌드박스가 Temp 폴더 권한을 망가뜨린 이력이 있으므로, 재검토 때는 Windows 복원 지점을 먼저 만든 뒤 시험한다.**
- **중단된 차례의 명령 (알려진 한계, 2026-10-06 확인):** Windows에서는 차례를 중단해도 Codex가 띄운 명령 프로세스가 끝나지 않는다. 연결부 점검에서 중단 76초 뒤 저장소에 파일이 생겼다. 대응: 래퍼가 중단 뒤 2분 동안 바뀐 파일을 `lateChanges`로 남기고, 마스터는 종료 코드 3이면 다시 시작하지 않고 그 목록과 함께 보고한다. 래퍼는 커밋되지 않은 변경이 있으면 새 대화를 거부하므로 늦은 변경은 다음 시작 때도 걸린다. 2분 뒤의 변경과 git이 무시하는 경로의 변경은 탐지하지 못한다.
- **서브에이전트가 작업 공간 밖에 영향을 준 사례 (2026-10-06):** 3단계 플러그인을 구현하던 수정 서브에이전트가 멈춘 테스트를 끝내려고 `taskkill //F //IM node.exe`를 실행해 PC의 node 프로세스를 모두 끝냈다. "작업 공간 밖에 영향을 주는 일은 사람을 호출한다"는 규칙을 지키지 않은 사례다. 대응: 차단 목록에 `Bash(taskkill *)`, `Bash(taskkill.exe *)`를 넣고(루트와 `project-template`), 규칙 파일에 "테스트에는 제한 시간을 두고, 프로세스는 자기가 띄운 PID로만 끝내며, 그래도 안 되면 멈추고 보고한다"를 넣었다. 남은 위험: 차단 목록은 Claude의 명령에만 걸린다. 서브에이전트가 다른 이름의 명령으로 같은 일을 할 수 있으므로 규칙 파일과 검수가 함께 막아야 한다.
