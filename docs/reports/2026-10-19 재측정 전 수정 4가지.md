## 1. 지적 확인

네 지적 모두 코드상 맞았다. 뺀 지적은 없다.

| 지적 | 확인한 내용 |
|---|---|
| S1 임시 정리의 링크 | `emptyDir`가 `existsSync`, `readdirSync`로 정리 루트를 열고 자식을 사용자 권한으로 재귀 삭제한다. 루트(`codex-tmp`)와 상위(`.superpowers`, `sdd`)의 링크는 확인하지 않는다. Node는 Windows junction을 `lstat().isSymbolicLink() === true`로 보고한다(10-19, Node 24.11.1에서 확인). 그래서 확인을 넣을 수 있다 |
| S2 설정·exclude 쓰기 | `readText`가 모든 읽기 오류를 `null`로 합친다. exclude는 그 값을 빈 문자열로 바꿔 덮어쓴다. `.codex/config.toml`, `.superpowers/sdd/.gitignore`, exclude는 실제 경로를 확인하지 않고 쓴다. 작업 폴더는 문자열로만 확인한다 |
| S4 무시된 보호 파일 | 보호 대조의 입력은 `git status`(무시 파일 제외)뿐이다. 해시는 `.codex/config.toml` 하나만 본다. 템플릿 `.gitignore`가 `.claude/settings.local.json`을 무시하므로 이 파일의 변경은 어디에도 잡히지 않는다. 또 `.claude/` 규칙은 경로 `.claude` 자체(링크로 바뀐 경우 git에 보이는 모양)에 걸리지 않는다 |
| C8 최종 수정 뒤 테스트 | 실행 스킬 마무리에서 마스터 전체 테스트는 최종 수정 앞(1번)에만 있다. 수정 뒤에는 Codex 쪽 테스트와 재검수뿐이다. 재개는 `Final review:` 줄이 있는지만 본다 |
| B1 템플릿 최초 진입 | 작업자 명세 2.1절은 프로젝트 CLAUDE.md에 계획·실행 스킬 규칙을 넣는다고 정했다. 그런데 템플릿에는 재개 규칙만 있다. 3단계 시험은 이 규칙을 따로 넣었다(작업자 명세 248줄) |

## 2. 바꾼 것

### 수정 1: 링크·경계 검사 (S1, S2)

- 새 모듈 `plugin/scripts/lib/safe-path.mjs`
  - `checkSafePath(경계, 대상)`: 대상이 경계 밖이면 거부한다. 경계 아래 각 단계를 `lstat`해 링크(junction 포함)가 있으면 거부한다. `lstat`가 ENOENT 밖의 오류를 내면 거부한다. 이미 있는 가장 깊은 경로의 실제 경로(`realpath`)도 경계 안이어야 한다.
  - `readExisting`: ENOENT만 "없음"(`null`)이다. 다른 읽기 오류는 던진다.
- 적용한 곳(`codex-run.mjs`, 모두 사용자 권한으로 쓰거나 지우는 곳)

  | 경로 | 경계 | 실패 시 |
  |---|---|---|
  | `.superpowers/sdd/codex-tmp` 만들기 | 저장소 | 준비 실패, 종료 코드 5 |
  | `.superpowers/sdd/codex-tmp` 정리(호출 뒤) | 저장소 | 지우지 않음, 종료 코드 5. 이유에 원래 결과를 덧붙임 |
  | `.codex/config.toml` 읽기·쓰기 | 저장소 | 준비 실패, 종료 코드 5 |
  | `.superpowers/sdd/.gitignore` | 저장소 | 준비 실패, 종료 코드 5 |
  | `info/exclude` 읽기·쓰기 | git 공용 폴더(`--git-common-dir`) | 준비 실패, 종료 코드 5 |
  | 작업 폴더(`--workspace`) 만들기 | 저장소 | 종료 코드 5 (요청 목록 밖이지만 같은 함수 안의 쓰기라 함께 넣음) |

- 정리 거부는 Codex 호출 뒤에 일어난다. 그래서 이미 커밋이 끝났을 수 있다. 결과 파일의 `commit`과 이유의 "원래 결과"로 알 수 있다.

### 수정 2: 보호 경로 확장 (S4)

- `protected.mjs`에 `snapshotProtected`를 더했다.
  - 저장소 최상위의 보호 폴더(`.claude/`, `.codex/`, `.githooks/`) 아래 모든 파일과 최상위 `CLAUDE.md`의 내용 해시를 적는다. git이 무시하는 파일도 포함한다.
  - 링크는 따라가지 않고 `link:<대상>`으로 적는다. 그래서 보호 폴더가 링크로 바뀌면 차이가 난다.
  - 없는 경로는 적지 않는다. 그 밖의 읽기 실패는 던진다.
- 래퍼의 호출 흐름(`run.mjs`)
  - 첫 호출 직전에 스냅샷을 찍는다. 읽기에 실패하면 Codex를 부르지 않고 종료 코드 5로 끝낸다.
  - 차례(첫 턴, 형식 정정, 불일치 정정)마다 다시 찍어 비교한다. 다르면 커밋하지 않고 종료 코드 3, 이유는 `보호 파일 변경: <경로들>`이다. 다시 읽기에 실패하면 종료 코드 3, 이유는 `보호 파일 확인 실패: ...`다.
  - 기존 `.codex/config.toml` 해시 확인(`projectConfigHash`)은 이 스냅샷에 들어가므로 없앴다.
- `findProtectedChanges`: 폴더 규칙(`.claude/`)이 경로 `.claude` 자체에도 걸리게 했다. git 대조에서 보호 폴더가 링크 항목으로 보이는 경우다.

### 수정 3: 템플릿 최초 진입 규칙 (B1)

### 수정 4: 최종 수정 뒤 마스터 테스트 (C8)

- 실행 스킬 마무리
  - 1번 마스터 테스트 뒤 `Master test: <통과 수>/<전체 수> 통과 — target <HEAD 7자리>` 줄을 쓴다.
  - 최종 검수 줄은 `Final review: <승인 | 수정 필요> — target <HEAD 7자리> — findings ...`다. 재검수 줄에도 target을 남긴다.
  - 최종 수정으로 HEAD가 바뀌었으면 재검수 뒤 그 HEAD에서 마스터 테스트를 다시 돌린다. Codex 테스트 결과로 대신하지 않는다. 실패하면 남은 지적으로 판정해 기록한다. 최종 보고에는 수정 뒤 결과를 적는다.
- 실행 스킬 재개: 마무리 줄의 결과와 target을 함께 본다. `Final review: 수정 필요`인데 `Final fix:` 줄이 없으면 최종 수정부터 한다. 최종 수정으로 HEAD가 바뀌었는데 그 HEAD의 `Master test:` 줄이 없으면 마스터 테스트부터 한다.
- 두 스킬의 종료 코드 표에 "보호 파일 변경(git이 무시하는 파일 포함)"과 "링크·경계 확인 실패(5)"를 반영했다.

## 5. 남은 한계 (재측정 뒤 분류할 때 함께 본다)

- 보호 폴더가 아주 크면(예: Claude Code의 `.claude/worktrees/`를 쓰는 경우) 호출마다 그 폴더 전체를 읽는다.
