## B. 문서 정합성

### B1. 높음 — 새 프로젝트의 최초 계획·실행 스킬 진입 규칙 누락

- **근거:** 작업자명세:49–51은 각 프로젝트 CLAUDE.md에 “계획은 codex-planning, 실행은 codex-execution, 원래 writing-plans/SDD는 쓰지 않는다”를 넣는다고 정한다. 실제 템플릿:21–29에는 계획 검토·측정 머리말과 **재개 시** 스킬 선택만 있다. 계획스킬:3·8, 실행스킬:195–196은 이미 그 스킬 안에 들어온 뒤의 제한이다.
- **문제:** 템플릿으로 새 프로젝트를 만들고 명세를 승인하는 정상 진입에는 원본 설계 스킬의 다음 단계를 대체할 명시적 프로젝트 규칙이 없다. 플러그인의 존재·설명만으로 선택이 보장되지는 않는다. **추측:** 자동 선택에 실패하면 Claude가 원래 계획/구현 경로로 들어갈 수 있다. 실제 재현은 하지 않았다. 비교 시험은 작업자명세:248에 따라 이 규칙을 별도로 추가했으므로 템플릿 자체의 충분성을 입증하지 않는다.
- **제안:** 템플릿에 최초 진입의 두 스킬과 대체할 원본 스킬을 명시한다. 재측정 준비에서 복사한 실제 규칙을 확인하고 변경 조건에 남긴다.

### B2. 중간 — 낡은 “빠른 참고”가 여전히 설계 기준으로 연결됨

- **근거:** 루트:12는 빠른참고를 “설계의 기준”으로 지정하지만 인계 머리말은 그 문서가 2단계 이전이며 인계·저장소 문서가 우선이라고 한다. 빠른참고:25·34·66·137은 큰 작업 사용자 계획 검토를 유지하고, 124는 Opus 구현 투입을 기본으로 두며 176은 “현재 1단계 직전”이다. 148·168–172는 구축 중 Plus 유지와 업그레이드 시점을 현재형으로 쓴다.
- **문제:** 프로젝트를 다시 읽는 사람과 AI가 가장 먼저 보는 문서가 최신 스킬·결정과 다른 기본 경로를 안내한다. 가격의 외부 진위를 확인한 지적이 아니라, 저장소 안에 기록된 Pro 전환과의 시점 불일치다.
- **제안:** 삭제보다 “초기 설계·현재 운영 기준 아님” 표시와 최신 명세/현황 링크를 붙인다. 루트의 기준 문서 포인터와 적용 우선순위를 갱신한다.

프롬프트별 확인: 계획 plan/fix/handoff와 실행 implement/fix/handoff/final-fix는 모두 설계 질문/브레인스토밍을 금지한다. 계획 plan과 실행 implement만 명시적인 NEEDS_CONTEXT/BLOCKED 진입 조건을 설명하고, 다른 수정 틀도 최종 STATUS 선택지에는 두 상태를 허용한다. 두 review-additions는 읽기 전용 검수 결과/판정만 요구하고 사용자에게 직접 질문하도록 지시하지 않는다. 따라서 **새로운 직접 사용자 질문 경로는 틀보다 마스터 스킬의 분기와 템플릿에 있다.**

**C1-지적 — 중간 / 명세 미기재를 계획 붕괴로 확대함**  
근거: 인계 §1 “작은 결정은 마스터 추천안/가정”; 계획스킬:100; 실행스킬:55–59.  
문제: 계획 단계에는 실행 단계의 “큰 문제 외에는 마스터 판정”과 같은 경계가 없다. 단순 구현 선택도 명세에 문장으로 없으면 사용자 재질문으로 갈 수 있다. 이는 실제 질문 빈도 측정이 아닌 **규칙상 경로** 지적이다.  
제안: 명세에 답이 없어도 되돌릴 수 있고 승인 범위 안인 선택은 마스터가 가정·이유·비용을 기록해 계속한다. 범위·보안·외부 영향·완료 기준을 바꾸는 결정만 계획 붕괴로 올린다.

**C2-지적 — 중간 / 사람이 직접 병합·게시하는지, 승인 후 AI가 하는지 미정합**  
근거: 인계 §1은 GitHub push를 사용자 직접 수행, §4 원칙 4는 “main 병합과 GitHub 게시는 사람이 한다”. 템플릿:39와 루트 안전 규칙은 “push와 merge는 사용자 승인을 받은 뒤에만 한다”. settings.json:26–28은 Claude에게 해당 명령의 승인을 요청하게 하고, 실행스킬:191은 병합 방식을 원본 스킬로 넘긴다.  
문제: “사용자 승인”과 “사용자 직접 실행”은 다른 권한 계약이다. 읽은 후속 문서에는 둘 중 어느 문구로 통일하는지와 변경 이유가 없다. 원래 인계 내부에도 “병합 승인/방식 선택”과 “사람이 한다”가 함께 있어 의도 해석이 필요하다. 실제 무승인 병합 사례를 발견한 것은 아니다.  
제안: 인계 갱신 때 merge와 push 각각의 실행 주체를 한 줄로 확정한다. 사람이 직접 push한다면 AI 선택지에서 push/PR 실행을 빼고 명령 안내만 남긴다.

### C4. 원칙 3 — 확인 실패가 통과로 읽힐 수 있는 문서 경로

**C4-1. 높음 — 최종 수정 뒤 독립 전체 테스트 근거가 빠질 수 있음**

- **근거:** 개선명세:199–201은 보정 없는 마스터 테스트를 최종 판단 기준으로 삼는다. 실행스킬:168은 이를 **최종 검수·최종 수정 전에** 배치한다. 170–174의 최종 수정/재검수 뒤 다음은 보고다. final-fix-prompt.md:7은 Codex에게 전체 테스트를 요구하지만 Codex 샌드박스 환경이다.
- **문제:** 마스터 테스트가 실패해 최종 수정에서 고쳤거나, 성공 후 최종 수정이 코드를 바꾼 경우 최종 HEAD의 보정 없는 전체 테스트 근거가 없다. 수정 전 결과나 보정된 Codex 결과가 “최종 판단”으로 대신 읽힐 수 있다. 실제 실패 배포 사례는 **확인 못 함**. 이후 원본 finishing 스킬이 이를 어떤 환경에서 보완하는지도 이번 대상 밖이라 **확인 못 함**이며, 우리 스킬의 최종 보고 시점은 그 호출보다 앞이다.
- **제안:** 최종 코드 변경이 끝난 뒤 마스터가 보정 없이 전체 테스트를 실행하고 커밋 해시와 결과를 기록한다. 통과하지 못하거나 실행 못 했으면 보고에 미검증/차단으로 남기고 완료·배포 가능 상태로 전이하지 않는다.

**C4-2. 중간 — “검수 기록 있음/판정함”과 “검수 통과”의 구분이 약함**

- **근거:** 계획스킬:68은 `Plan review:` 줄이 있으면 다시 검수하지 말라고 한다. 실행스킬:117도 `Final review:`의 존재를 기준으로 재검수를 건너뛰고 다음 마무리를 찾는다. 실제 기록은 승인/수정 필요 모두 `<결과>`에 들어간다. 실행스킬:129는 diff로 확인 못 한 항목을 마스터가 확인하도록 하지만, 마스터도 확인 못 한 경우의 상태를 따로 정하지 않는다. 174는 최종 재검수의 남은 지적을 판정·기록하고 두 번째 수정은 하지 않는다.
- **문제:** 재실행 방지는 필요하지만 줄의 존재만으로 결과 성공을 판단해서는 안 된다. 남은 Critical/Important, 테스트 실패, 확인 불가가 “Ruling으로 처리됨”이라는 이유만으로 종료될 수 있는 문서상 여지가 있다. 인계의 5라운드 상한/마스터 판정 결정 자체를 위반으로 세지는 않는다. 실제로 실패 결과를 승인으로 오독한 사례는 **확인 못 함**.
- **제안:** 기록된 결과·열린 지적·다음 작업을 구분해 재개한다. 확인 불가 또는 배포를 막는 실제 중요 결함은 상한 도달 시 “판정 후 완료”가 아니라 명시적 차단/사용자 결정으로 종료한다. 추가 수정 횟수를 무조건 늘릴 필요는 없다.

**C4-3. 중간 — 파일 목록이 같다는 이유로 시간 초과 뒤 상태가 안정됐다고 판단**

- **근거:** 계획스킬:38·66, 실행스킬:46·115은 `git status`와 멈출 때의 남은 변경 목록을 비교한다. 흐름:41은 실제 시간 초과 후 남은 변경이 0개였다고 한다. 작업자명세:291은 2분 뒤 변경과 무시 경로의 변경은 탐지 못 한다고 명시한다.
- **문제:** 이미 수정된 같은 파일에 이전 명령이 더 써도 변경 파일 목록/상태 문자는 같을 수 있다. 아직 쓰지 않고 실행 중인 명령도 목록에는 안 나타난다. 반대로 새 변경이 반드시 이전 명령의 작업이라는 단정도 근거가 부족하다. **추측:** 이런 경우 새 호출과 이전 명령이 겹칠 수 있다. 이번에는 프로세스 확인·재현을 하지 않았다.
- **제안:** 문구를 “목록상 새 파일 없음, 이전 명령 종료는 별도 확인 필요”로 좁힌다. 재개 조건에 추적 가능한 실행 상태와 변경 내용 기준을 포함하고, 확인 못 하면 사람이 판단하도록 한다. 기존 프로세스를 강제로 종료하라는 제안은 아니다.

**C4-4. 중간 — 확인 실패 경고를 비용·안전 집계의 정상 0과 구분해야 함**

- **문제:** 결과 보존은 필요하지만 하위 기록 확인 실패가 있으면 토큰 합계·위험 명령 수를 완전한 측정값으로 볼 수 없다. “Codex 작업 완료”와 “집계/안전 확인 완료”의 다른 상태가 보고에서 뭉칠 수 있다. 상세 구현 오류 여부는 이번 범위 밖이다.
- **제안:** 재측정 보고에는 불완전 집계/확인 불가를 별도 표시하고 0건·완전 합계로 비교하지 않는다. 반드시 필요한 안전 판단이 불가능하면 중단 원칙을 적용한다.

실패로 해석하지 않아도 되는 사례도 있다. 변경 없는 반박은 검수자가 근거를 판단하므로 실패가 아니고, 재시도한 일시 오류 후 정상 완료를 인정하는 규칙은 작업자계획:25·작업자명세:100에 이유가 기록돼 있다. 네트워크 허용과 하위 에이전트 설정 차단 실패도 숨겨진 성공이 아니라 문서에 명시된 한계다. 다만 이 한계를 상위 보고에서 “전부 차단”으로 요약해서는 안 된다.
