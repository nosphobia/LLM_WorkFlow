## 2. 확인한 사실 (2026-10-10, 토큰을 쓰지 않는 확인만)

### 2.1 Codex 하위 에이전트를 끄는 방법

Codex 0.160에는 `multi_agent` 기능 설정이 있고 지금 켜져 있다(안정 기능). 끌 수 있는 길은 셋이다.

| 길 | 확인 결과 |
|---|---|
| 대화마다 `config` 인자 (`thread/start`, `thread/resume`) | 프로토콜은 받는다. 그러나 공식 플러그인의 대화 실행 함수(`runAppServerTurn`)가 이 인자를 넘기지 않는다. 쓰려면 래퍼가 그 함수 대신 프로토콜을 직접 다뤄야 한다 |
| 프로젝트 설정 `.codex/config.toml` | Codex가 읽는다. 단, 신뢰한 프로젝트에서만 적용한다. 신뢰 등록은 Codex가 대화를 시작할 때(`thread/start`, 토큰을 쓰지 않음) 스스로 한다. 실험 저장소에서 시작 전에는 "비활성", 시작 뒤에는 "활성"이 됐다 |
| 사용자 설정 `~/.codex/config.toml` | 사용자의 다른 프로젝트에도 적용되므로 쓰지 않는다 |

- 실제로 하위 에이전트 도구가 사라지는지는 아직 확인하지 않았다. Codex 차례를 한 번 돌려야 한다(질문 4).
- 신뢰 등록의 부수 효과: 래퍼나 점검을 쓴 저장소는 모두 사용자 Codex 설정의 신뢰 목록에 자동으로 들어가 있다. 연결부 점검 임시 저장소 5개, 탐색 저장소(`codex-probe`), 시험 저장소, 확인 실험 저장소 2개(10-09, 10-10)다. 지금까지의 래퍼 호출에서도 일어나던 일이다.

### 2.2 한도를 미리 읽는 방법

- 공식 플러그인이 내보내는 클라이언트로 `account/rateLimits/read`를 부르면 토큰 없이 5시간·주간 한도와 풀리는 시각을 읽을 수 있다.
- 지금 상태: 5시간 5% 사용, **주간 97% 사용(10-14 12:31에 풀림)**, 요금제 plus.

### 2.3 3단계 시험의 호출별 사용량 (Plus, 하위 에이전트 포함)

| 호출 | 5시간 한도 증가 | 주간 한도 증가 |
|---|---|---|
| 계획 작성 (첫 호출) | 77% → 한도 도달 (+23 이상, 미완) | 기록 없음 (최대 +4) |
| 계획 이어가기 | +7 | +1 |
| 계획 수정 1 | +7 | +2 |
| Task 1 / 2 / 3 / 4 / 5 | +16 / +9 / +18 / +15 / +15 | +3 / +2 / +3 / +2 / +3 |
| 최종 수정 | +27 | +4 |

작업 5개에 5시간 한도의 약 80%가 들었다. 최종 수정까지 한 5시간 창 안에 들어가지 않는다. 하위 에이전트를 끄면 줄어들 것으로 보지만 측정 전이다.

### 2.4 정리 실패 처리의 설계 재료

- Python 3.13의 `mkdtemp`가 만든 폴더는 샌드박스 안에서 지우지 못한다. 보통 방법으로 만든 폴더는 샌드박스 안에서도 지워진다(10-07 Codex의 `mkdir`/`rmdir` 확인).
- 래퍼가 브로커 환경으로 TEMP를 바꾸면 Codex 명령에 전달된다. 하지만 브로커와 Codex 자체의 임시 파일까지 따라 옮겨진다.
- 프로젝트 설정의 `shell_environment_policy.set`을 쓰면 Codex가 실행하는 명령에만 환경 변수를 줄 수 있다(설정 항목은 확인했고, 실제 적용은 질문 4의 확인 대상).

## 3. 질문

### 질문 1. 하위 에이전트를 끄는 방법
- **A. 래퍼가 관리하는 프로젝트 설정 파일 (추천)**
  - 래퍼가 호출 전마다 `.codex/config.toml`(git 무시)을 쓴다.
  - `config/read`로 "활성"과 값이 맞는지 확인하고, 아니면 종료 코드 5로 멈춘다.
  - 첫 호출 전에는 토큰 없는 대화 시작으로 신뢰 등록을 먼저 해 둔다.
  - `.codex/`는 보호 경로에 넣는다.
- **B. 래퍼가 대화를 직접 시작:** 공식 함수 대신 프로토콜을 직접 다뤄 대화마다 `config`를 넣는다. 플러그인 내부 의존과 코드가 늘어난다.
- **C. 지시문과 탐지 경고만**

어느 안이든 11번 탐지(하위 에이전트가 생기면 경고)는 넣는다.

### 질문 2. 정리 실패 처리 (보완 1)
- **A. 권한 제한 없이 만들기 (추천)**
  - Codex 명령에만 Python 보정 모듈(`sitecustomize`)을 얹어, 임시 폴더를 Python의 권한 제한 없이 만들게 한다. 그러면 샌드박스 안에서도 정리가 성공한다.
  - 임시 폴더 위치(TEMP)는 저장소 안 git 무시 폴더로 정한다.
  - 호출 뒤 래퍼가 그 폴더를 사용자 권한으로 비우고 결과 파일에 기록한다.
  - 결과물 코드는 그대로이고, 샌드박스 밖(마스터의 테스트)에서는 보정이 없다.
  - 대가: 임시 폴더가 Python의 제한 대신 저장소 폴더의 권한을 따른다.
- **B. 정리 오류만 무시**
  - 보정 모듈은 정리 오류만 무시하고 권한 제한은 유지한다.
  - 폴더가 매번 남고, 호출 뒤 래퍼가 지운다.
  - `TemporaryDirectory` 말고 `mkdtemp`와 `rmtree`를 직접 쓰는 테스트는 여전히 실패한다.

A와 B 모두 질문 1의 A(프로젝트 설정)로 명령에만 환경을 준다. 질문 1이 B면 대화 설정으로, C면 브로커 환경으로 준다.

### 질문 3. 한도 확인 기준값 (Plus 기준, 2.3절 근거)
- **A. 제안값 (추천)**
  - 계획 작성 전: 5시간 남은 양 50% 이상, 주간 남은 양 10% 이상.
  - 실행 전: 5시간 남은 양이 작업 수 × 18% 이상(최대 100%), 주간 남은 양이 작업 수 × 3% + 7% 이상.
  - Codex 호출마다: 5시간 30%, 주간 5% 미만이면 그 호출 전에 멈추고 풀리는 시각을 알린다. 가장 큰 단일 호출이 27%였으므로, 호출 도중 한도에 걸려 작업이 반쯤 남는 일을 막는다.
- **B. 시작 전 두 번만 확인 (호출마다 확인 없음)**

### 질문 4. Codex를 쓰는 확인의 시점 (지금 주간 97% 사용)
