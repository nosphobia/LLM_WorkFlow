## 3. Codex 한도로 멈춘 뒤 "이어서 진행"으로 재개할 수 있는가

**이번 시험의 두 번의 멈춤은 남은 파일만으로 재개할 수 있었다.** 다만 그것은 마스터가 스스로 상태를 자세히 적었기 때문이다. 스킬이 보장하지는 않는다.
- 계획 단계 멈춤: `planning.md`에 대화 ID, 커밋되지 않은 계획 파일, 멈춘 이유가 있었다.
- 마무리 단계 멈춤: `progress.md`에 최종 검수 결과, 판정, 최종 수정 대상과 준비된 지시 파일, "한도가 풀리면 `start --role final-fix`", 브로커를 닫지 않았다는 사실이 있었다.

**부족한 항목:**
1. **마무리 단계의 진행 줄이 정해져 있지 않다.**
   - 작업 루프는 `Task <N>: complete` 같은 정해진 줄로 재개한다.
   - 마무리 단계에는 정해진 줄이 없다: 최종 검수(결과, 지적 파일), 최종 수정(대화 ID, 커밋), 재검수, 측정점 3, 사용량 기록 커밋, 브로커 종료.
   - 그래서 새 세션이 Opus 최종 검수를 다시 돌릴 수 있다.
2. **멈춤 기록의 형식이 없다.** 멈출 때 원인, 재개 조건, 다음 명령(전체 인자)을 진행 기록에 쓰라는 규칙이 없다.
3. **새 세션의 재개 진입 규칙이 없다.**
   - "이어서 진행"을 받았을 때 계획 단계면 `codex-planning`, 실행 단계면 `codex-execution`으로 들어가 진행 기록의 마지막 줄부터 이어간다는 규칙이 없다.
   - 실행 준비 5단계(충돌 점검 표)를 이미 있으면 건너뛰라는 말도 없다.
4. **계획 단계의 끊김 처리가 판정에만 의존한다.** 계획 파일이 커밋되지 않은 채 한도로 끊긴 경우의 처리는 스킬에 없고, 이번에는 `[Task 6 판정 적용]` 판정으로 처리했다.

**비용 면의 덧붙임:** 이번에는 대기 뒤 같은 세션을 이어가 대화 전체(17만~18만 토큰)를 다시 캐시에 썼다. 진행 기록만 읽는 새 세션으로 재개하면 다시 읽을 양이 훨씬 적다. 1~3번을 보완하면 오래 멈춘 뒤에는 새 세션에서 재개하라고 안내할 수 있다.

## 4. 임시 폴더 원인

### 4.1 남은 폴더 6개의 기록

기록하려고 보니 폴더 6개는 이미 지워져 있었다. 시험 저장소 최상위의 수정 시각은 10-09 16:11이다. 그래서 소유자는 기록하지 못했다. 이 세션에서 앞서 남긴 한 폴더(`tmp4e0nl5as`)의 `icacls` 결과는 다음과 같다.

```
NT AUTHORITY\SYSTEM:(OI)(CI)(F)
BUILTIN\Administrators:(OI)(CI)(F)
OWNER RIGHTS:(OI)(CI)(F)
```

대신 4.2절의 재현 실험으로 같은 권한의 폴더를 만들어 소유자까지 기록했다.

### 4.2 재현 실험

- 장소: OS 임시 폴더의 조사용 저장소 `C:\Users\Beneche\AppData\Local\Temp\llm-workflow-tempprobe-5wUBFi\repo`. 시험 저장소는 건드리지 않았다.
- 방법:
  - 래퍼 `start --role check --effort low`로 두 번 불렀다.
  - 두 번째는 브로커를 닫은 뒤 TEMP와 TMP를 저장소 안의 git 무시 폴더 `.codex-tmp`로 지정해 새 브로커가 그 값을 물려받게 했다.
  - 실험이 만든 폴더는 기록한 뒤 사용자 계정으로 지웠고, 브로커는 닫았다.

| 항목 | 기본 환경 | TEMP를 `.codex-tmp`로 지정 |
|---|---|---|
| 샌드박스 안 TEMP | `C:\Users\Beneche\AppData\Local\Temp` | `...\repo\.codex-tmp` |
| `tempfile.gettempdir()` | 사용자 Temp | `.codex-tmp` |
| `mkdtemp()`가 만든 위치 | `...\Temp\probe-gkx352uy` | `...\repo\.codex-tmp\probe-dy3enfzv` |
| 샌드박스 안 `icacls` | 액세스 거부 | 액세스 거부 |
| 샌드박스 안 삭제 | 실패 (WinError 5) | 실패 (WinError 5) |
| 폴더 소유자 | Beneche\Beneche | Beneche\Beneche |
| 폴더 권한 (SDDL) | `D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;FA;;;OW)` | 같음 |
| 사용자 계정으로 삭제 | 성공 | 성공 |
| Codex 토큰 | 169,300 | 170,190 |

- 샌드박스 안에서는 `whoami`도 실패했다(Win32 오류 5).
- TEMP를 지정하자 브로커의 세션 폴더(`cxc-*`)와 Codex 자체의 임시 폴더(`.tmp*`)도 `.codex-tmp`에 생겼다. 환경 변수가 브로커와 Codex 앱 서버 전체에 적용되기 때문이다.

### 4.3 가설 판정

- **"Python 3.13의 `tempfile.mkdtemp`가 Windows에서 새 폴더의 권한을 제한한다(CVE-2024-4030 대응)":** 맞다.
  - 실험 폴더의 권한이 남은 폴더와 같았다(SYSTEM, Administrators, 소유자만, 상속 차단).
  - 소유자가 사용자 계정이어도 Codex 샌드박스의 제한된 권한으로는 지우지 못한다.
  - 사용자 계정으로는 지울 수 있다.
- **"샌드박스 안에서 TEMP에 쓸 수 없어 현재 폴더(저장소 최상위)로 대체됐다":** 틀렸다.
  - 샌드박스 안의 TEMP는 쓸 수 있었다.
  - 실제로는 Codex가 직접 옮겼다. 계획 자체 점검에서 기본 임시 폴더의 정리가 실패하자 "Python 기본 임시 폴더는 쓰기 불가"라고 판단했다(10-07 15:24:44 Codex 메시지). 그 뒤 계획의 테스트 코드를 `TemporaryDirectory()`에서 `TemporaryDirectory(dir=Path.cwd())`로 바꿨다(15:24:51 패치).

### 4.4 결론

TEMP를 지정해도 잠김은 풀리지 않고 남는 위치만 바뀐다. 저장소 최상위 대신 무시 폴더에 남는다는 이점은 있지만, 브로커 파일까지 저장소 안으로 옮겨진다. 문제의 핵심은 두 가지다.
1. Python 임시 폴더 정리는 샌드박스 안에서 늘 실패한다.
2. Codex가 이 실패를 잘못 해석해 위치를 옮기고, 막히자 권한 변경까지 시도했다.

| 5. 명세 경계 조건 점검 목록 | 포함 (작게) | `project-template` CLAUDE.md에 "명세를 쓸 때 출력 인코딩, 줄 나누기, 반올림, 표기 예시를 정했는지 확인한다" 한 줄. 4단계에서 도메인 프로필로 옮긴다 | 재측정은 같은 명세를 쓰므로 비용 비교에 영향이 없다 |
| 6. 래퍼의 Codex TEMP 지정 | 제외 | 대신 Codex 공통 지시에 넣는다: "임시 폴더를 저장소 안으로 옮기지 않는다. 지우지 못한 파일이나 폴더는 권한을 바꾸거나 다른 명령으로 우회하지 말고 CONCERNS에 적는다" | 4.4절: TEMP 지정은 잠김을 풀지 못하고 브로커 파일까지 옮긴다 |
| 7. 마스터의 기계적인 일을 밖으로 | 포함 | ① 작업 하나의 "지시 파일 뽑기 + Codex 지시문 채우기 + 래퍼 실행 + 결과 요약"을 한 명령으로. ② "검수 묶음 + 검수 지시문 채우기"를 한 명령으로. ③ 진행 기록 줄을 정해진 형식으로 쓰는 명령(8번과 공유). Codex로 옮길 일은 없다 | 1절: 67회, 비용 43%. 마스터에게는 검수자 호출, 판정, 사용자 보고만 남긴다 |
| 8. 재개 절차 | 포함 | 3절의 부족 항목 4개: 마무리 단계 진행 줄, 멈춤 줄 형식(`멈춤: <원인> — <재개 조건> — <다음 명령>`), 새 세션 재개 진입 규칙(충돌 점검 표가 있으면 건너뜀), 계획 단계 끊김 처리. 멈출 때 사용자에게 "새 세션에서 '이어서 진행'"을 안내한다 | 대기 후 재개가 비용의 34% |
| 9. 시작 전 Codex 한도 확인 | 보류 | 기록만 한다 | 우선순위 낮음, Pro 전환 예정 |
| 10. Codex 하위 에이전트 금지 (새 후보) | 포함 권장 | Codex 공통 지시에 "하위 에이전트를 만들지 않는다. Superpowers 스킬이 위임을 지시해도 직접 한다"를 넣는다 | 2절: 17개, 토큰 24% 증가. 하위 에이전트의 작업은 래퍼 집계 밖이다 |
| 11. 래퍼 토큰 집계에 하위 에이전트 포함 (새 후보) | 포함 (필수) | 래퍼가 `parent_thread_id`로 하위 에이전트 기록을 찾아 토큰을 더하고, 네트워크와 위험 명령 탐지도 그 기록까지 본다 | 재측정을 토큰으로 비교하므로 없으면 비교가 틀린다 |
| 12. 위험 명령 탐지 확대 (새 후보, 명세 9.2절 2번 포함) | 포함 권장 | 프로세스 종료(`taskkill`, `Stop-Process`, `kill`)와 권한 변경(`takeown`, `icacls /grant`, `Set-Acl`), 삭제 우회(.NET 삭제 함수)를 탐지해 경고로 남긴다 | 비교 보고서 4절의 권한 변경 시도. 경고만 남기므로 재측정 비용에 영향이 없다 |
| 13. 보호 경로 대조 (명세 9.2절 1번) | 선택 | 래퍼가 Codex 변경 파일을 보호 경로(`.claude/`, `.githooks/`, `CLAUDE.md`)와 대조해, 걸리면 커밋하지 않고 실패 처리한다 | 앞서 첫 개발 작업 후보로 정한 항목이다. 정상 작업에서는 걸리지 않으므로 재측정에 영향이 없다 |

### 5.2 개발과 재측정 방법

- **개발 방법:** LLM_WorkFlow 자체 개발에 플러그인을 쓰는 것은 보류 중이다. 그래서 원래 Superpowers 방식으로 개발 worktree에서 한다. 범위가 여러 스킬과 래퍼에 걸치므로 큰 작업으로 보고 진행한다: 명세 → 계획 → 구현 → 단위 테스트와 연결부 점검 → 배포.
- **재측정:**
  - 같은 명세로 새 시험 프로젝트를 만든다. 폴더를 만들 때 승인을 받는다.
  - 마스터는 Opus 그대로 둔다.
  - 바꾼 조건은 5.1절에서 포함한 항목뿐이고, 재측정 보고서에 목록으로 적는다.
  - Codex는 하위 에이전트를 포함한 토큰으로 비교한다.
  - 대기는 사용자 응답 대기와 Codex 한도 대기로 나눠 적는다.
  - 실행 중 지휘를 Sonnet으로 낮추는 것은 이번에 시험하지 않고 열린 질문으로 남긴다.
