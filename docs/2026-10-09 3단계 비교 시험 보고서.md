### 3.2 Claude 사용량

측정 구간은 계획 작성 시작(스킬 호출)부터 최종 보고 뒤 첫 사용자 메시지까지다. 계획 구간은 실행 스킬 호출 전까지다.

| 합계 토큰 | 11,860,077 | 16,104,861 |

| 최종 검수 (Opus) | 약 $0.58 | 약 $1.16 |

**늘어난 원인:**
1. **긴 대기 뒤 캐시 재작성:** 마스터 세션의 캐시는 1시간이면 끝난다. 3단계 마스터는 1시간이 넘는 대기 뒤 캐시를 세 번 새로 썼다(계획 승인 대기 21시간, 질문 대기 1.9시간, Codex 한도 대기 4.5시간). 이 세 번이 약 42만 토큰(약 $3.4)으로, 마스터 캐시 쓰기의 3분의 2다. 2단계에는 이런 재작성이 없었다.
2. **마스터의 일이 늘었다:** 메인 세션 호출이 40회에서 96회로 늘었다. 마스터는 Codex 지시 파일, 맥락 파일, 검수 틀을 쓰고, 보조 스크립트를 만들고, 래퍼 결과를 읽었다.
3. **독립 계획 검수가 더해졌다:** 약 $1.11. 설계상 새로 넣은 비용이다.
4. **구현자 교체로 아낀 몫이 작다:** 2단계 구현자는 주로 Haiku여서 Task 1~4 구현이 약 $0.37에 그쳤다. Codex로 바꿔도 아낄 수 있는 Claude 비용이 거의 없었다.

**측정 방법과 한계:**
- 메시지 하나가 여러 줄로 기록되므로 메시지 ID로 묶었다.
- 서브에이전트 기록의 출력 토큰은 스트림 시작 때 값만 남아 실제보다 작다. 두 시험 모두 같은 한계가 있다. 입력 측 토큰과 메인 세션의 출력 토큰은 정확하다.
- 단가는 공개 API 가격(백만 토큰당 입력/출력)이다: Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 4.5 $1/$5. 캐시 읽기는 0.1배, 캐시 쓰기는 5분짜리 1.25배, 1시간짜리 2배다.
- 이 환산은 두 시험을 비교하기 위한 추정이다. 구독 사용률이 이 비율대로 움직인다는 보장은 없다.

## 4. 관찰 항목

- **PowerShell 파이프 한글 문제:** Codex(PowerShell)는 프로그램의 기본 출력(cp949)을 정상으로 읽었다. 한글이 깨진 쪽은 Claude의 Git Bash였다. 이것이 최종 검수 중요 #1이 됐다.
  - 마스터는 "지금대로 둔다"로 판정했다.
  - 사용자가 PowerShell에서 직접 실험해 판정을 확인했다(10-09): 출력을 UTF-8로 강제하면 PowerShell 캡처가 깨졌다.
  - 2단계 프로그램은 같은 지적을 받고 UTF-8로 강제했다(`397b090`). 그래서 PowerShell에서 결과를 변수로 받을 때 깨질 수 있다. 확인은 하지 않았다.
- **Codex가 보고한 우려와 판정:**
  - 계획 작성 때 저장소 안에 남은 빈 임시 폴더: 보고만 했다.
  - Task 5의 줄바꿈 경고와 임시 폴더: 환경 요인으로 기각했다.
  - 최종 수정 때 평균이 아주 클 때의 Decimal 정밀도: 실제 입력에서 생기지 않으므로 고치지 않는다고 판정했다.
- **판정 목록:** 계획 1건(`[Task 6 판정 적용]`), 실행 4건이다. Task 4의 임시 폴더 삭제 대비, 중요 #1 인코딩 유지, 최종 수정 범위 축소, Decimal 우려 기각이다.
- **래퍼의 형식 위반 정정:** 0회. 네트워크 명령 경고도 0회다.
- **`[Task 6 판정 적용]`:** 1건이다. 계획 작성이 한도에 걸려 커밋되지 않은 계획 파일이 남았고, 같은 대화를 이어 계획을 완성했다. 이후 계획 검수 지적 4건이 수정 1라운드로 해결됐으므로 문제가 없었다.
- **보호 파일 확인:**
  - 방법: 명세 사본 커밋(`532dfb5`) 이후 시험 브랜치의 모든 커밋과 병합 결과에서 `git log`와 `git diff`로 `.claude/`, `.githooks/`, `CLAUDE.md`의 변경을 찾았다. 최초 커밋(`76e4462`)부터도 함께 확인했다.
  - 결과: 변경이 없다.
- **Codex 명령 점검 (안전):** Codex 세션 기록 7개, 도구 호출 180회를 확인했다.
  - 프로세스 종료, push, merge, 커밋 명령은 없다.
  - 저장소 밖에 쓴 기록도 없다.
  - 자기가 남긴 임시 폴더를 지우려고 했을 때는 경로가 작업 폴더 안인지 먼저 확인한 뒤 시도했다.
- **새로 확인한 위험 (Codex 샌드박스가 남긴 잠긴 폴더):**
  - Codex가 계획을 자체 점검하는 중에 만든 빈 `tmp*` 폴더 6개가 시험 저장소 최상위에 남았다.
  - 폴더 권한에는 SYSTEM, Administrators, 소유자만 있고 사용자 계정 항목이 없다. 그래서 Codex도 지우지 못했고, 일반 계정으로도 지우지 못할 수 있다.
  - 이 PC에서 `elevated` 샌드박스가 Temp 폴더 권한을 망가뜨린 이력과 같은 계열의 문제다.

합의한 규칙대로 하면 **전환은 보류하고 원인부터 고친다.**

## 6. 다음 결정을 위한 정리

구조 자체(역할 분리, 래퍼, 검수, 멈춤 규칙)는 품질과 안전 면에서 의도대로 동작했다. 남은 문제는 비용이다. 원인별 대응 후보는 다음과 같다.

1. **긴 대기를 줄이거나 대기 뒤 재작성을 줄인다:** 이번 차이의 가장 큰 단일 원인이다. Codex 한도 대기와 사용자 질문 대기가 실행 중에 생기지 않게 하는 방법(한도 확인 뒤 시작, 질문이 필요한 판단을 계획 검토 관문으로 앞당기기)을 검토한다.
2. **마스터의 기계적인 일을 스크립트로 옮긴다:** Codex 지시 파일, 검수 자료 묶음, 결과 요약을 래퍼나 스크립트가 만들게 하면 Opus 메인 세션의 호출 수가 준다.
3. **Codex 쪽 비용을 줄인다:** 첫 계획 호출 하나가 5시간 한도를 다 썼다. 호출 하나의 기본 비용이 약 100만 토큰(대부분 캐시 입력)이다. 계획 작성의 추론 강도나 맡기는 범위를 다시 정할지 검토한다.
4. **명세 단계를 보강한다:** 두 시험 모두 같은 네 가지 주제(출력 인코딩, 줄 나누기, 반올림, 표기 예시)에서 최종 검수 지적을 받았다. 명세 단계에서 이런 경계 조건을 정하게 하면 작업자와 무관하게 최종 수정이 줄어든다.

이번 시험은 작은 기능 하나다. 작업이 커서 구현 비중이 큰 경우에도 같은 결과일지는 확인하지 않았다.
