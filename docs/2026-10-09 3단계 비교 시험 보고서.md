### 1.2 계획 검토 관문 판정

- **관문을 연 목적:** Opus 계획 검수가 사용자 검토를 대신할 수 있는지 확인하는 것이었다.
- **확인 방법:** 세션 기록에서 관문 보고(10-07 18:00)부터 승인(10-08 15:22)까지의 사용자 메시지와 질문 도구 응답을 모두 찾았다.
- **결과:** 사용자는 수정을 요청하지 않았다. 승인 메시지는 "클로드는 초기화돼서 0%야. 진행해" 한 줄이었다. 관문 보고에는 작업 목록, Opus 검수 지적 4건과 수정 결과, 판정 1건이 들어 있었다.
- **판정:** 이번 한 번의 사례에서는 Opus 계획 검수가 사용자 검토를 대신했다. 관문의 비용은 21시간 대기와 그 뒤 캐시 재작성 71,482 토큰(약 $0.57)이었다.

### 1.3 측정 구간과 명세 단계

이번 시험은 2단계 명세를 그대로 써서 명세 단계를 건너뛰었다. 그래서 측정 구간에 명세 단계의 질문과 답이 없었다. 측정 구간(계획 작성 시작부터 최종 보고까지)은 두 시험 모두 명세 단계를 포함하지 않는다. 실제 사용에서는 명세 질답 중에도 사용자 응답 대기가 생기므로, 대기로 인한 비용은 이번보다 클 수 있다.

**늘어난 원인:**
1. **긴 대기 뒤 캐시 재작성:** 마스터 세션의 캐시는 1시간이면 끝난다. 3단계 마스터는 1시간이 넘는 대기 뒤 캐시를 네 번 새로 썼다(1.1절 표: Codex 한도 대기 2번, 사용자 응답 대기 2번). 이 네 번이 467,923 토큰(약 $3.7)으로, 마스터 캐시 쓰기 649,638 토큰의 72%다. 2단계는 구간 시작 때 한 번(54,287 토큰, 약 $0.43)이었다.
   - 처음 보고서에는 세 번(약 42만 토큰, 약 $3.4)으로 적었다. 5만 토큰보다 큰 쓰기만 셌기 때문에, 10-07 15:28~17:45 대기 뒤의 42,026 토큰이 빠졌다.
2. **마스터의 일이 늘었다:** 메인 세션 호출이 40회에서 96회로 늘었다. 마스터는 Codex 지시 파일, 맥락 파일, 검수 틀을 쓰고, 보조 스크립트를 만들고, 래퍼 결과를 읽었다.
3. **독립 계획 검수가 더해졌다:** 약 $1.11. 설계상 새로 넣은 비용이다.
4. **구현자 교체로 아낀 몫이 작다:** 2단계 구현자는 주로 Haiku여서 Task 1~4 구현이 약 $0.37에 그쳤다. Codex로 바꿔도 아낄 수 있는 Claude 비용이 거의 없었다.

**측정 방법과 한계:**
- 메시지 하나가 여러 줄로 기록되므로 메시지 ID로 묶었다.
- 서브에이전트 기록의 출력 토큰은 스트림 시작 때 값만 남아 실제보다 작다. 두 시험 모두 같은 한계가 있다. 입력 측 토큰과 메인 세션의 출력 토큰은 정확하다.
- 단가는 공개 API 가격(백만 토큰당 입력/출력)이다: Opus 5.5 $4/$20, Sonnet 5.5 $2/$10, Haiku 4.5 $1/$5. 캐시 읽기는 0.1배, 캐시 쓰기는 5분짜리 1.25배, 1시간짜리 2배다.
- 이 환산은 두 시험을 비교하기 위한 추정이다. 구독 사용률이 이 비율대로 움직인다는 보장은 없다.

## 4. 관찰 항목

- **PowerShell 파이프 한글 문제:** Codex(PowerShell)는 프로그램의 기본 출력(cp949)을 정상으로 읽었다. 한글이 깨진 쪽은 Claude의 Git Bash였다. 이것이 최종 검수 중요 #1이 됐다.
  - 마스터는 "지금대로 둔다"로 판정했다.
  - 사용자가 PowerShell에서 직접 실험해 판정을 확인했다(10-09): 출력을 UTF-8로 강제하면 PowerShell 캡처가 깨졌다.
  - 2단계 프로그램은 같은 지적을 받고 UTF-8로 강제했다(`397b090`). 그래서 PowerShell에서 결과를 변수로 받을 때 깨질 수 있다. 확인은 하지 않았다.
- **Codex가 보고한 우려와 판정:**
  - 계획 작성 때 저장소 안에 남은 빈 임시 폴더: 보고만 했다.
  - Task 5의 줄바꿈 경고와 임시 폴더: 환경 요인으로 기각했다.
  - 최종 수정 때 평균이 아주 클 때의 Decimal 정밀도: 실제 입력에서 생기지 않으므로 고치지 않는다고 판정했다.
- **판정 목록:** 계획 1건(`[Task 6 판정 적용]`), 실행 4건이다. Task 4의 임시 폴더 삭제 대비, 중요 #1 인코딩 유지, 최종 수정 범위 축소, Decimal 우려 기각이다.
- **래퍼의 형식 위반 정정:** 0회. 네트워크 명령 경고도 0회다.
- **`[Task 6 판정 적용]`:** 1건이다. 계획 작성이 한도에 걸려 커밋되지 않은 계획 파일이 남았고, 같은 대화를 이어 계획을 완성했다. 이후 계획 검수 지적 4건이 수정 1라운드로 해결됐으므로 문제가 없었다.
- **보호 파일 확인:**
  - 방법: 명세 사본 커밋(`532dfb5`) 이후 시험 브랜치의 모든 커밋과 병합 결과에서 `git log`와 `git diff`로 `.claude/`, `.githooks/`, `CLAUDE.md`의 변경을 찾았다. 최초 커밋(`76e4462`)부터도 함께 확인했다.
  - 결과: 변경이 없다.
- **Codex 명령 점검 (안전):** 메인 대화 기록 7개(도구 호출 180회)와 하위 에이전트 기록 17개(도구 호출 74회)를 확인했다.
  - 프로세스 종료, push, merge, 커밋 명령은 없다. 저장소 밖에 쓴 기록도 없다.
  - **권한 변경 시도 (계획 작성 중, 10-07 15:25~15:28):** Codex가 자기가 남긴 임시 폴더 6개를 지우려고 다음을 차례로 시도했다.
    1. 경로가 작업 폴더 안인지 확인한 뒤 PowerShell `Remove-Item -Force`를 실행했다. Codex 자체의 명령 검사가 거부했다.
    2. .NET 삭제 함수(`[System.IO.Directory]::Delete`)로 다시 시도했다.
    3. 소유권 가져오기(`takeown.exe`)를 시도했다.
    4. 권한 부여(`icacls /grant`)를 시도했다.
    5. 정리를 하위 에이전트에게 맡겼다. 하위 에이전트는 확인 명령 2개만 실행하고 한도에 걸려 멈췄다.
  - 모두 작업 폴더 안의 자기 산출물이 대상이었고, 모두 권한 거부로 실패했다. 다만 막힌 명령을 다른 명령으로 바꿔 다시 시도하고 권한까지 바꾸려 한 것은, 명세 8절의 두 서브에이전트 사례와 같은 "혼자 수습하려는" 유형이다.
  - 처음 보고서의 점검(7개, 180회)은 이 명령들을 찾는 패턴에 넣지 않았고, 하위 에이전트 기록도 보지 않았다.
- **임시 폴더가 남은 원인 (재현 실험으로 확인):**
  - 폴더 6개는 기록하기 전에 이미 지워져 있었다(저장소 최상위 수정 시각 10-09 16:11). 처음 기록한 한 폴더의 권한은 SYSTEM, Administrators, 소유자(OWNER RIGHTS) 전체 권한뿐이었다.
  - Codex는 계획에 든 테스트 코드를 실행했는데, 기본 임시 폴더에서 정리가 실패하자 "임시 폴더에 쓸 수 없다"고 잘못 판단했다. 그래서 테스트 코드를 `TemporaryDirectory(dir=Path.cwd())`로 바꿔 임시 폴더를 저장소 최상위로 옮겼고, 거기서도 정리가 실패해 6개가 남았다.
  - 잠기는 이유: Python 3.13의 `tempfile.mkdtemp`는 Windows에서 새 폴더를 SYSTEM, Administrators, 소유자만 쓸 수 있게 만든다(CVE-2024-4030 대응, 권한 `D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;FA;;;OW)`). Codex 샌드박스의 제한된 권한으로는 이 폴더를 지우지도, 권한을 읽지도 못한다.
  - 소유자는 사용자 계정(Beneche)이다. 그래서 일반 사용자 계정으로는 바로 지울 수 있다. 처음 보고서의 "일반 계정으로도 지우지 못할 수 있다"는 틀렸다.
  - 샌드박스 안의 TEMP는 원래 사용자 Temp 폴더이고 쓸 수 있다. "샌드박스가 TEMP에 쓸 수 없어 현재 폴더로 대체됐다"는 가설은 맞지 않았다. 상세 실험은 추가 분석 문서에 있다.

## 6. 다음 결정을 위한 정리

구조 자체(역할 분리, 래퍼, 검수, 멈춤 규칙)는 품질과 안전 면에서 의도대로 동작했다. 남은 문제는 비용이다. 원인별 대응 후보는 다음과 같다.

1. **긴 대기를 줄이거나 대기 뒤 재작성을 줄인다:** 이번 차이의 가장 큰 단일 원인이다. Codex 한도 대기와 사용자 질문 대기가 실행 중에 생기지 않게 하는 방법(한도 확인 뒤 시작, 질문이 필요한 판단을 계획 검토 관문으로 앞당기기)을 검토한다.
2. **마스터의 기계적인 일을 스크립트로 옮긴다:** Codex 지시 파일, 검수 자료 묶음, 결과 요약을 래퍼나 스크립트가 만들게 하면 Opus 메인 세션의 호출 수가 준다.
3. **Codex 쪽 비용을 줄인다:** 호출 하나의 기본 비용이 약 100만 토큰(대부분 캐시 입력)이다. 게다가 Codex가 하위 에이전트를 17번 만들어 토큰이 24% 늘었다. Codex 쪽 Superpowers 스킬(하위 에이전트 위임을 지시하는 스킬)을 호출마다 2~5개 읽은 것이 원인이다. 래퍼 지시문에서 하위 에이전트를 금지할지 검토한다.
4. **명세 단계를 보강한다:** 두 시험 모두 같은 네 가지 주제(출력 인코딩, 줄 나누기, 반올림, 표기 예시)에서 최종 검수 지적을 받았다. 명세 단계에서 이런 경계 조건을 정하게 하면 작업자와 무관하게 최종 수정이 줄어든다.

이번 시험은 작은 기능 하나다. 작업이 커서 구현 비중이 큰 경우에도 같은 결과일지는 확인하지 않았다.
