## 1. 최종 목표 (사용자의 말 그대로의 의도)

- **사용자는 마스터 AI와만 소통한다.** 소통 시점은 **처음의 명세 단계**와 **마지막의 배포 단계** 두 곳이다.
- 그 사이(기획, 개발, QA, 위키)는 **마스터 AI가 자동으로 진행**한다. 정말 중요한 사항이 아니면 사용자에게 묻지 않는다.
- **마스터 AI는 Claude**다.
- **비용 때문에, 기획과 개발 등 대부분의 작업은 Codex가 주력으로 한다.** 검수는 Claude가 한다.
- 구독 플랜의 사용량 안에서 운영한다. 현재 Claude Pro + ChatGPT Plus이고, 워크플로우가 갖춰지면 Claude Max + ChatGPT Pro($100)로 올릴 예정이다.
- 분야와 무관한 범용 멀티 에이전트 워크플로우다. 주 용도는 로블록스 게임과 데스크톱 프로그램이고, 웹사이트와 영상(코드 기반)은 이후 확장한다. 분야별 세부 환경은 "도메인 프로필"로 분리한다.

### 목표로 하는 사용자 개입 지점

| 시점 | 사용자가 하는 일 |
|---|---|
| 명세 | 마스터와 질답, 명세 승인. 작은 결정은 마스터가 추천안으로 정하고 명세서의 "가정" 목록에 적는다. 사용량 시작값도 이때 알려준다. 큰 작업이라도 계획 검토는 기본으로 하지 않는다. 계획을 보고 싶으면 이때 "이번엔 계획도 보여줘"라고 요청한다 |
| 중간 | 정말 중요한 문제가 생겼을 때만 (되돌릴 수 없는 작업, 보안 관련, 작업 공간 밖 영향, 계획이 망가진 경우) |
| 배포 | 최종 QA("사람 확인" 항목만 직접 확인)와 병합·배포 승인. 사용량 끝값도 이때 알려준다. GitHub push는 사용자가 직접 한다 |

## 2. 출발점과 큰 방향

- 출발점은 유튜브 영상(youtu.be/woSiT_kytXo)의 에이전트 워크플로우다: 마스터 AI, 기획 → 개발 → 독립 QA → 위키, 작업자-검수자 쌍, 교차 모델 검수, 작업별 기록.
- 처음부터 새로 만들지 않고, **검증된 오픈소스 하네스 Superpowers를 골조로 삼아** 영상에만 있는 좋은 요소를 얹는다.
- **Superpowers 원본 파일은 수정하지 않는다.** 바꿔야 하는 단계는 우리 스킬로 만들어 대체한다 (업데이트 시 덮어써짐 방지, 원인 추적 용이).
- 이전에 만들던 SDD 파이프라인과 Claude/Codex 토론 프로토콜은 전면 폐기했다.

### 비교표 밖의 주요 결정

- **도메인 프로필:** 분야별 QA 도구, 테스트 명령, 규칙을 프로필로 분리. 처음 한 번 마스터와 함께 만들고 사용자 승인 후 Git에 고정해 재사용 (즉석 생성 금지). 첫 프로필은 로블록스(공식 Script Sync + Studio MCP).
- **새 프로젝트 생성 자동화:** 마스터와 짧은 질답 → 스크립트가 폴더·템플릿·Git 설정 → VS Code 새 창 + project-brief로 맥락 전달. 설계 문서는 프로젝트 지식의 "새-프로젝트-생성-자동화-설계.md". 아직 구현 전.
- **로컬 LLM:** 파이프라인 밖의 독립 도구로 나중에 추가 (사전 정의 프롬프트 + 호출 스크립트). "큰 입력 → 작은 출력" 작업만 (로그 요약 등). 보조 PC(RTX 3080)에 LM Studio 서버.
- **사용량 기록:** 가볍게. 기능당 한 줄(`workflow/usage-log.md`). 호출별 Codex 기록은 진행 기록 폴더의 별도 파일.
- **저장소:** LLM_WorkFlow와 각 프로젝트는 별개의 Git 저장소. 모노레포는 쓰지 않음 (AI 맥락 오염, 권한 정책, 브랜치 혼재, 외주 납품 문제).

## 4. 핵심 원칙

1. **연결선은 코드로 지킨다.** 프롬프트(규칙 문장)로만 지키는 관문은 새어 나간다. 중요한 관문은 스크립트, 훅, 차단 규칙으로 강제한다 (그래프 엔지니어링의 "어떤 결정을 모델에게 맡기지 않을 것인가").
2. **쓰기는 한 모델(Codex), 검수는 다른 회사 모델(Claude)이 깨끗한 맥락에서, 읽기 전용으로.**
3. **실패하면 멈춘다.** Codex 호출이 실패하거나 한도에 걸리면 Claude가 대신 구현하지 않고 멈춰서 보고한다. 판단 근거가 없으면 실패로 처리한다.
4. **사람의 최종 손은 main과 배포.** main 병합과 GitHub 게시는 사람이 한다.
5. **각 단계는 이전 단계가 실제로 잘 돌아가는 것을 확인한 뒤에만 넘어간다.**
6. **복잡도를 경계한다.** 효과가 확인되지 않은 층은 빼는 것도 허용한다.

## 5. 안전장치와 알려진 한계

**안전장치**
- Claude 차단 규칙: 강제 push, main push, `git reset --hard`, `rm -rf`, `.env`·`secrets/` 읽기·쓰기, PowerShell 도구 전체, `powershell`·`pwsh`·`cmd`(.exe 포함) 호출, `--no-verify`, `taskkill`(.exe 포함). push와 merge는 "확인" 규칙.
- Git pre-push 훅: main으로의 push 거부 (`core.hooksPath .githooks`). 사용자만 `git push --no-verify`로 통과.
- 실제 비밀 정보는 프로젝트 폴더에 두지 않는다.
- 관리자 권한 터미널을 쓰지 않는다.
- 테스트와 오래 걸리는 명령에는 제한 시간. 프로세스는 자기가 띄운 PID로만 끝낸다.

**알려진 한계 (기록됨)**
- Claude 차단 규칙은 Codex에 적용되지 않는다. Codex는 자기 샌드박스로만 제한된다.
- Codex 샌드박스(unelevated)는 저장소 밖 쓰기와 `.git` 쓰기는 막지만 **네트워크와 프로세스 종료는 막지 못한다.** 네트워크 명령은 래퍼가 탐지해 경고한다.
- elevated 샌드박스는 보류: 이 PC에서 예전에 Temp 폴더 권한을 손상시킨 이력이 있다. 5단계 전 재검토 시 복원 지점을 만든 뒤 시험.
- 시간 초과로 중단해도 Codex가 실행한 명령은 계속 돌 수 있다. 래퍼가 중단 후 늦은 변경을 탐지해 보고한다.
- 사고 사례 2건 (모두 원래 Superpowers 방식으로 Claude 서브에이전트가 구현하던 중): `taskkill /F /IM node.exe`로 PC의 node 전체 종료, 상대경로 리다이렉트로 `D:\tmp_unused` 생성.

## 6. 운영 방식

- `D:\Work\LLM_Project\LLM_WorkFlow`는 **항상 main**인 운영 폴더. 설치된 플러그인이 이 폴더를 실시간으로 읽는다. 여기서 직접 수정하지 않는다.
- 워크플로우 개발은 `LLM_WorkFlow-dev` worktree의 작업 브랜치에서 한다. 개발 사본 시험은 `claude --plugin-dir <dev>\plugin` (VS Code 확장에서는 이 플래그를 줄 수 없으므로 터미널 CLI에서).
- **배포 = main 병합.** 배포 후 연결부 점검(`codex-check.mjs`)을 돌린다. 배포는 작업 마지막에 한 번, 작업을 동시에 둘 이상 돌리지 않는다.
- Claude Code 세션은 반드시 작업할 프로젝트 폴더에서 시작한다 (상위 폴더에서 시작하면 그 프로젝트의 규칙이 빠진다).
- 버전 고정: 양쪽 Superpowers 6.4.1(커밋 5bf4e78), Codex 플러그인 1.0.4, Claude 쪽 자동 갱신 끔. 업데이트는 의도적으로 하고, 그때마다 연결부 점검을 다시 돌린다.

**비교 시험 후 반영할 것:** 계획 스킬에서 사용자 계획 검토 관문을 기본 해제하고, 명세에서 요청한 작업만 열도록 바꾼다 (3절 8번). 이번 비교 시험에서는 Opus 계획 검수가 사람의 검토를 대신할 수 있는지 확인하기 위해 관문을 한 번 연다.

**비교 시험 후 결정할 것:** LLM_WorkFlow 자체 개발도 우리 플러그인으로 할지(결정 기준은 3단계 명세에 있음). 첫 개발 작업 후보는 "보호 파일 변경 차단"(래퍼가 Codex의 변경을 `.claude/`, `.githooks/`, CLAUDE.md 등 보호 경로와 대조해 거부)과 "프로세스 종료 명령 탐지".
